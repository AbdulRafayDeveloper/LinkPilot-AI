## Project identity

**LinkPilot AI** (`package.json` name: `linkpilot-ai`) is a set of exactly **9 LinkedIn tools**. Eight of them take pasted LinkedIn text and generate copy the user posts themselves; the ninth makes the image that goes with a post:

| Route | Tool | What it generates |
|---|---|---|
| `/trending-topics` | Trending Topics | 6 fresh, source-backed web/AI/SaaS topics from live web research, each with a ready-to-post LinkedIn post |
| `/post-image-creator` | Post Image Creator | a clean post image in the user's own brand colours, with their own photo in it, from whatever the post is about (`/post-image-creator/history` is the gallery of what it has made) |
| `/connection-note` | Connection Note | ≤300-char invite note, 8 tones (incl. Recently Funded: congratulate a funded decision maker and offer to help; Hiring Startup: match a hiring startup's need, portfolio link, 15 minute call; Post Interaction and Comment Interaction: thank someone who engaged with your post or your comment) |
| `/comment-writer` | Comment Writer | a comment on someone's post (text or screenshot), 8 tunes (incl. Value Add, Supportive and Relatable) |
| `/post-comment-replies` | Post Comment Replies | a reply to one comment, 2 contexts × 6 tones (Show Expertise, Ask Their Opinion, Give Useful Tips, Share Real Example, Politely Disagree, Invite to DM), written as Abdul Rafay to the other person's latest comment |
| `/follow-up-message` | Follow-Up Message | a follow-up from a pasted conversation, 2 types |
| `/first-message` | First Message | a first DM from a profile, 8 tones (Curiosity Hook default; Post Interaction and Comment Interaction are the Curiosity Hook opening with a thank-you; Viewed + Accepted is a soft offer of help to someone who viewed your profile and accepted your request) |
| `/inmail-message` | InMail Composer | subject + message from a profile, 8 tones (Trigger Event default; Post Interaction, Comment Interaction and Viewed + Accepted open with a fixed thank-you or "I noticed you viewed my profile" sentence, the same `OPENING_LINES` First Message has, put back in code by `lib/openingLine.ts`, and their prompts come from `scripts/add-inmail-interaction-tones.mjs`) |
| `/conversation-reply` | Conversation Reply | analysis + next reply from a conversation, 6 tones (Validate + Share Pattern default) |

**`src/constants/linkedinTools.ts` is the app's one navigation source.** It holds `TOOL_GROUPS`, the four sidebar headings, and two lists: `LINKEDIN_TOOLS` (the 9 LinkedIn tools, all in the `linkedin` group; their order is the sidebar's only, and has nothing to do with where the app opens) and `APP_TOOLS` (those plus every other module, in sidebar order). `APP_TOOLS` alone drives the sidebar, the Jump to a tool switcher, the sitemap, the manifest shortcuts and `SEO_PAGES`, so a tool added there appears in all of them at once and can never exist in one surface and be missing from another. ## Commands

```bash
npm install          # .npmrc sets legacy-peer-deps=true; LangChain peer ranges conflict without it
npm run dev          # next dev (Next.js 16, Turbopack) → http://localhost:3000
npm run build        # production build (build.bat just runs this)
npm run start        # serve the production build
npm run lint         # runs bare `eslint` (flat config; Next 16 no longer ships `next lint`)
npx tsc --noEmit     # type-check; there is no script for it
```

- Next 16 allows only one `next dev` per project folder. If another one is running, use it instead of starting a second.
- If `next dev` answers **every** route with the app's 404 page (API routes too, while files in `public/` still load), its `.next` cache is stale (it happened after `npm run build` ran while a dev server was up). Stop the dev server, delete `.next` and start it again; the code isn't the problem. Prefer running `npm run build` while no dev server is running.
- `tsc` also checks the generated `.next/types/validator.ts`. After you delete a route it reports stale "Cannot find module" errors until the next `npm run build` regenerates that file.
- **`tests/` is the owner's own and never leaves this machine**: `.gitignore` excludes it, so it is not in the repository and collaborators do not get it (it was removed from the index, not from disk). A new test file there is ignored by `git add` on purpose; never force-add one. One-off scripts left in the project root (`*.local.mjs`, `*.out`) are ignored too, and belong in a session's scratchpad rather than the root.
- `npm test` runs `node --test tests/`: plain `node:test` files (`tests/*.test.mjs`) that load the app's TypeScript through `tests/load.mjs` (jiti, already installed with Tailwind, with the `@/` alias), for logic that needs no server or database (Groq key rotation, model priority rules, source attribution and token usage, generation records keeping `_id` and their provider, no Gemini left). Everything else is verified by calling the API routes, or by using the pages, against a running server.

## Deploying (the owner's rule: GitHub `main` first, always)

- **Production is built from GitHub `main`, never from a working tree.** The Vercel project is connected to the repository, so pushing to `main` starts the production deployment by itself (it shows as the `linkedin-pilot-ai-git-main-…` alias). The order is always: green checks, commit, push to `main`, then watch that deployment reach Ready. Don't run `vercel deploy --prod` from a working tree: it uploads files git doesn't have, so the live site and GitHub drift apart, and a build that only passes because of an uncommitted file hides a broken `main`.
- **Green means the committed tree, not the working one.** `tsc`, `eslint` and `npm test` must pass on what is being pushed. When a commit takes only some of a shared file's changes, check the result in a clean checkout of the commit (`git worktree add --detach`), because a hunk from another session can reference code that isn't committed. That is exactly how `main` once failed to build while the live site looked fine.
- **After a deploy nothing is left behind:** `git status` is clean (ignored files such as `tests/` and root `*.local.mjs` scratch don't count) and `git rev-list origin/main..main` is empty. Several sessions share this tree, so anything still uncommitted belongs to someone; say whose rather than leaving it unexplained.
- The `vercel` CLI is still the tool for reading a deployment: `vercel ls`, `vercel inspect --logs <url>` for a failed build, and environment variables.

## Environment

`src/config/env.ts` is the only place that reads env vars. It is a Zod schema where blank values count as unset.
- Every URL, secret and model name comes from env, and none has a fallback value in code. Never hardcode one or add a default.
- A missing required var makes the app refuse to start, with an error that names it.
- `env.ts` is server-only. Client components get the site name from `config/site.ts`, never from env.
- Every var must also be documented in `.env.example`, and `.gitignore`'s `.env*` rule also ignores that file, so add `!.env.example` if it needs to be committed.

| Var | Purpose |
|---|---|
| `NEXT_PUBLIC_BASE_URL` | **Required.** Public origin for canonical links, the sitemap, robots and JSON-LD (exported as `SITE_URL`). |
| `MONGODB_URI` | **Required.** The `LinkPilot` database: every prompt, Trending history, Dummy Data and every tool's saved outputs (see Database). |
| `AUTH_SECRET` | **Required.** Signs the session cookie (at least 32 characters). Changing it signs every account out. |
| `ALLOW_SIGNUP` | `"true"` opens `/signup`, which creates `user` accounts. Anything else keeps sign-up closed and accounts come from the scripts. |
| `GROQ_API_KEY_1`, `GROQ_API_KEY_2` … + `GROQ_MODEL` | **Primary** provider for every module (Groq). **Any number of keys**: every `GROQ_API_KEY_<n>` that is set is read (`numberedKeys`), so adding `_8` or `_10` needs no code change; only `_1` is required (see AI architecture). Today there are 7, each from a **different Groq account** (the old account's keys 2 to 4 were dropped, since they shared key 1's limit). `GROQ_MODEL` (e.g. `openai/gpt-oss-120b`) writes every text and runs live research with Groq's browser search, so it must support that tool. |
| `GROQ_VISION_MODEL` | Reads screenshots (Comment Writer, Post Comment Replies) on Groq, e.g. `qwen/qwen3.8-27b`. Without it screenshots go to the next provider. |
| `GROQ_TRANSCRIPTION_MODEL` | Reads speech on Groq (Whisper, e.g. `whisper-large-v3-turbo`). |
| `OPEN_SOURCE_BASE_URL` + `OPEN_SOURCE_MODEL` (+ optional `OPEN_SOURCE_API_KEY`) | The fallback once every Groq key is used up: an open-source model on any OpenAI-compatible server (Ollama `http://localhost:11434/v1`, LM Studio, vLLM). Text only, no web search, screenshots or speech. Unset, it is skipped. |
| `OPENAI_API_KEY` + `OPENAI_LIGHTWEIGHT_MODEL` | **Last fallback** (GPT-4o Mini), plus OpenAI web search for research and vision for screenshots. |
| `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET_NAME` | Important Files storage. Server-only, read in one place (`services/storage/s3.ts`). Without all four, that module says so and every other module carries on. |
| `OPENAI_IMAGE_MODEL` | The image model Post Image Creator draws with, through the OpenAI Images API on the same `OPENAI_API_KEY`, e.g. `gpt-image-1`. Without it that module says so and every other module carries on. |
| `OPENAI_TRANSCRIPTION_MODEL` | Reads speech (voice input on Prompt Creator, Client Messaging, Message Rewriter and Client Voices) when Groq can't, e.g. `gpt-4o-mini-transcribe`. |
| `OPENAI_EMBEDDING_MODEL` | Turns a meeting into vectors for its chat (e.g. `text-embedding-3-small`). Groq has no embedding model, so this is OpenAI's; without it a meeting cannot be asked questions and every other module carries on. |

Model names live **only** in env. Never hardcode a model id in code. **Groq's free tier limits the organization, not the key**: every key made in the same Groq account shares one set of limits (for `openai/gpt-oss-120b`, 8,000 tokens a minute and 200,000 a day), so extra keys only add capacity when they come from different Groq accounts. One browser-search research pass can use 100,000 tokens or more. Once the day's tokens are used, Groq answers 429 "tokens per day", every key rests and the next provider writes.

## AI architecture (`src/services/ai.ts`)

- **Providers:** `MODEL_PROVIDERS = ["groq", "open-source", "openai"]` (`constants/aiProviders.ts`, `AiProviderId`; `AI_PROVIDERS` / `ModelProvider` in `services/ai.ts`) is the full set and `DEFAULT_MODEL_ORDER` the order **every module** uses, for every regular user. Don't add other providers (Gemini, Grok/xAI, Anthropic, etc.) without being asked. A provider is skipped when it isn't configured for the call (`isProviderConfigured(provider, input)`: a screenshot needs `GROQ_VISION_MODEL` on Groq, and the open-source model never reads one).
- **The order comes from the request, not from each function (`lib/modelOrder.ts`).** Every AI route resolves the order once, `modelOrderFor(viewer, moduleId)` (`services/modelPriority.ts`: the admin's saved order for that module when the account is an admin, otherwise the default), and runs its service inside `withModelOrder(order, () => …)`, an `AsyncLocalStorage`. Everything the work calls, however deep (humanizing, lead signals, rewrites, research, screenshots, speech), reads `currentModelOrder()`, which is the default outside a request. A new AI route must wrap its service call the same way, and its module id must be in `AI_MODULE_IDS` (`constants/modelPriority.ts`) with its `AI_MODULE_NEEDS`.
- **Every AI response says where it came from, and every AI call is counted (source attribution and budget tracking).**
  - **Recording is central.** The four places that call a provider (`invokeStructured` in `services/ai.ts`, the research passes in `services/liveResearch.ts`, `transcribeWithGroq` / `transcribeWithOpenAI`, and `generateImage` in `services/imageGeneration.ts`) each call `recordAiUsage({ provider, model, kind, usage, keyNumber?, audioSeconds? })` (`services/aiUsage.ts`) as soon as a provider answers. That notes the provider on the running request (`noteProviderAnswered`) and writes one row to `ai_usage` (`models/AiUsage.ts`): account, module, provider, model, `kind` (text, screenshot, web-search, speech, image), input, output and total tokens, seconds of speech, and for Groq which key answered. Tokens come from whatever the SDK reports, read by `readTokenUsage` (`lib/aiUsage.ts`: LangChain `usage_metadata`, chat-completions `usage`, OpenAI images and transcription `usage`); nothing is guessed, and a failed write is logged and never fails the call. Structured output is invoked with `includeRaw: true` for the usage, and `parsedOf` throws when the answer didn't parse, so the fallback still works. Groq speech uses `verbose_json` for the duration and OpenAI speech `json`. The prompt and the answer are never recorded.
  - **Every AI route runs its service through `runAiRequest(viewer, module, run)`** (`services/modelPriority.ts`): it resolves the order, runs the work inside `withModelOrder` with the module and account, and returns `{ result, source }`. `withSource` spreads the source onto the result, so the route answers (and saves) `{ ...result, provider, providers }` (`AiSource` in `types/ai.ts`): `provider` is the last provider that answered (rewrites and humanizing come last, so it wrote what is shown), `providers` every provider that answered, once each. A new route or provider is attributed with no code of its own; a module whose calls have no order to choose is a `UsageOnlyModuleId` (`post-image-creator`). Result types extend `WithAiSource` (both fields optional, so older saved results still fit). Meetings add each call's source to the meeting (`noteAnalysisSource`, `analysisProvider` / `analysisProviders`, cleared on Re-analyse), since an analysis is built over many calls; Meeting Planner's source is saved inside `prep`; Trending's inside the saved result (`TrendingResultSchema` `provider` / `providers`, optional).
  - **The page shows it with `components/ui/AiSourceLabel`** ("Source: Groq", or "Source: OpenAI (Groq also answered)"; `describeSource` in `constants/aiProviders.ts`; nothing for an unknown or missing provider) at the end of each result's meta line: `GeneratedResultPanel` takes a `source` prop, and Connection Note, Follow-Up, Post Comment Replies, Comment Writer, InMail, Client Messaging, Message Rewriter, Post Image Creator, Prompt Creator, Trending Topics, the Client Voices task list and each transcript, the meeting analysis and the meeting preparation each render it. `VoiceRecorder` shows the source of the last recording beside its limit (`showSource={false}` where the page names it itself, Prompt Creator). The "view all" pages show it as a pill in Details: every generation record copies `result.provider` into a top-level `provider` as it is validated (`recordModel` in `models/GenerationRecords.ts`, added with `schema.path`, never by merging a schema, which would drop `_id` and make every save fail), and `SavedOutput.provider` carries it.
  - **Budget view:** `GET /api/admin/ai-usage?days=1|7|30` (admin only, `AI_USAGE_DAYS`) sums `ai_usage` per provider (calls, input, output and total tokens, speech seconds, images) and per module and provider; `components/admin/AiUsagePanel` shows it at the top of AI Model Priority (a card per provider on a phone, a table from `md`).
- **Groq keys (`withGroqKey` in `services/ai.ts`, `lib/keyRotation.ts`, `services/groqKeyState.ts`):** every Groq call (structured output, research, transcription), from every module, runs through `withKeyRotation` over `GROQ_API_KEYS` (`config/env.ts`: every `GROQ_API_KEY_<n>` set, in number order, blanks and a key set twice left out). **A call starts on the active key, the one that answered last, and goes round from there** (`keyOrder` with `start`): with keys 1 to 3 used up and key 4 answering, every call goes straight to 4, then 5, 6, 7, and after the last key comes the first again. A failure that belongs to the key (`isKeyLimitError`, `lib/providerErrors.ts`: 401/403, 429, or a 413 per-minute token ceiling) rests that key (`keyRestMs`: 10 minutes rejected, 15 minutes over a daily limit, otherwise the provider's Retry-After or 60s) and hands the **same call** to the next key, which becomes the active key once it answers; anything else (a bad request, a timeout) is thrown at once. Rested keys are tried last, never skipped, so a call is never refused while one might answer. Only when every key has failed does the error reach `generateStructuredWithFallback`, which moves to the next provider. Each switch logs `🔑 Groq key 4 (4 of 7) failed (…); trying key 5`, with anything key-like redacted.
  - **The active key and the rests are shared by every server instance** (`provider_key_states`, `models/ProviderKeyState.ts`, one document for `groq`): read into memory at most every 15 seconds, written only when something changes (a key is set aside, or a different key starts answering), never on an ordinary call, and a database that can't be reached leaves each process on its own copy rather than failing a call. Keys are named there by a 16-character SHA-256 fingerprint, never their value or their number (a number moves when keys are added or removed). This is the app's "global state" for keys on purpose on the **server**: keys are secrets and must never reach the browser, so there is no client store (Redux or otherwise) for them. `GET /api/ai-status` says how many keys are set (`groqKeys`) and which number calls start from now (`groqActiveKey`).
- **The open-source model** (`createOpenSourceModel`) is `ChatOpenAI` pointed at `OPEN_SOURCE_BASE_URL`, so it answers in the same shape as OpenAI; structured output uses `method: "functionCalling"`, which OpenAI-compatible servers support most widely.
- `createGroqModel(apiKey, …)`, `createOpenSourceModel()` and `createOpenAIModel()` are the only places a LangChain chat model is constructed.
- `generateStructuredWithFallback({ schema, name, messages, validate?, providers?, input?, onFallback?, timeoutMs?, signal? })` is how every module generates. It tries the request's order (`providers` overrides it; `input: "image"` for a screenshot). If a provider isn't configured, fails on every key, times out (default 45s), returns output that fails the schema, or fails `validate`, it moves to the next. It throws `UserFacingError` when no provider is configured. `onFallback` lets streaming tools show "switching to the backup model".
- **Retries (standard exponential backoff with full jitter, `lib/retry.ts` `withRetry`; only transient failures, `lib/transientErrors.ts` `isTransientError`: 408/425/429/5xx, dropped connections, Mongo network errors; never bad keys, 400s, used-up quotas, timeouts or aborts):**
  - AI calls: `withProviderRetry` retries a provider twice (research passes once) and honours `Retry-After` (a wait over 8s isn't waited out), around the Groq key rotation and before the next provider. A daily quota ("per day", TPD) is not retried. LangChain's own retries are off (`maxRetries: 0`) so they never stack.
  - MongoDB: `connectDB` retries the connection twice and never caches a failed one. Grounding-link resolving retries once.
  - Browser: every call to our API goes through `fetchWithRetry` / `requestApi` (`lib/apiClient.ts`), and so does every direct request to storage (a file preview, copying an image, the brand photo PUT). GET/PUT/DELETE retry twice on network errors and 408/429/502/503/504; a 500 or any other 4xx is never retried. A POST retries only when it says so:
    - `{ retry: true }`: the request saves nothing, or the server already makes a repeat harmless. The SSE tools (only before the stream starts), voice transcription, Client Voices tasks, meeting preparation (`claimPrepRun`) and analysis (resumable), sign-out, finishing an upload, a brand photo upload plan, and a plan link's Reset today.
    - `{ idempotent: true }`: anything that creates a record, and every JSON generator (`hooks/useGenerationRequest`, whose routes save a record and cost an AI call). The client makes one `Idempotency-Key` per call and sends the same key on every retry. Used by the Daily Tasks, Quick Notes, Meetings, Meeting Planner, Clients, Dummy Data, Reference Content, Employees and Important Content creates, the employee plan link (a repeated New link would otherwise break the link just issued) and starting an upload.
    - No retry at all: sign-in and sign-up, where a repeat would count a wrong attempt twice.
  - **Idempotency keys (`services/idempotency.ts`, `models/IdempotencyKey.ts`, collection `idempotency_keys`):** a route that creates something exports `POST = withIdempotency("<route>", handlePost)`, which leaves the handler unchanged. Keys are scoped per account, route and key (unique index), and the account is checked before any lookup, so a signed-out request never gets a stored answer. The first attempt claims the key and runs; a 2xx answer is stored (up to 512 KB, a larger one replays as 409 "already saved") and a repeat gets it back marked `Idempotent-Replayed: true` without running. A repeat while the first is still running gets 503 + `Retry-After: 2`. Any non-2xx answer (a 400 the user will correct, a cancelled 499, a 5xx) or a thrown error releases the key, and a claim older than 6 minutes counts as abandoned. Keys expire after 24 hours (TTL index). A request without the header runs exactly as before. The streaming routes are not wrapped: a stream can't be replayed. A new create route or generator must be wrapped, and its client call must pass `idempotent: true`.
  - Storage: the S3 client retries every call itself (`maxAttempts: 3`, standard mode: throttling, 5xx and dropped connections). The server reads a stored file through the SDK (`getObjectBytes`), never with a single `fetch` of a signed link. In the browser, `lib/assetUpload.ts` sends a small file in one PUT and a large one in parts, both through `sendPart`: `withRetry` backoff on a dropped connection or 408/429/5xx, never on a refusal that won't change (an expired link) or a cancellation.
  - The bucket's CORS rule decides which sites may upload at all (see Important Files). A browser upload from an origin it doesn't list fails as "The connection to storage dropped" after its retries, whatever the code does.
- **Audio** doesn't go through the chat models: Groq reads a recording with Whisper through its own SDK (`transcribeWithGroq`, `groq-sdk`, `GROQ_TRANSCRIPTION_MODEL`, every key) and OpenAI through its transcription endpoint (`transcribeWithOpenAI`, `OPENAI_TRANSCRIPTION_MODEL`), both under `withProviderRetry`, because LangChain has no speech-to-text interface. Voice input uses them (see Voice input).
- **A failure says what to fix, never just "please try again".** When every provider fails, `generateStructuredWithFallback` throws a `UserFacingError` built by `describeProviderFailure` (`lib/providerErrors.ts`): the provider rejected the key (names `GROQ_API_KEY_1 to GROQ_API_KEY_5`, `OPEN_SOURCE_API_KEY` or `OPENAI_API_KEY`), has no such model (names the model variable), is out of quota, is rate limiting, timed out or had a 5xx, and a provider skipped for missing configuration is named as "not tried". Anything that looks like a key is redacted first (`redactSecrets`), so the message is safe to show. A module that wraps a failure in its own message uses `asUserFacingError` (`lib/errors.ts`), which keeps this specific reason and only falls back to the general message when there is nothing better to say; Image generation and OpenAI transcription describe their failures the same way.
- **`GET /api/ai-status`** says what a deployment is configured to do: each provider configured or not, the variable names each one is waiting for, how many Groq keys are set (never which), and whether transcription, screenshots, image generation and file storage are available. Names and yes or no only, never a value. It is the first thing to open when a tool works locally and fails on the host.
- `services/senderGuard.ts` wraps it for outreach tools. It detects invented claims about the sender (the `SENDER_CLAIM` regex) and asks for one rewrite.
- Shared fabrication checks, each comparing the output against the tool's sources: `lib/figures.ts` (`findUnsupportedFigures`: a number + unit no source contains) and `services/userClaims.ts` (`findUnsupportedUserClaims`: sentences about the user's work the sources don't support; `findInventedProof`: case studies, "a similar company", "in half"). Post Comment Replies, Conversation Reply and Follow-Up use them to trigger a targeted rewrite and to validate the humanized text. Reuse them instead of writing new regexes.
- `services/liveResearch.ts` (`runLiveResearch`) handles web research for Trending Topics, Comment Writer and Post Comment Replies:
  - It tries the providers that can search, in the request's order: Groq (`GROQ_MODEL` with `tools: [{ type: "browser_search" }]`, `tool_choice: "required"`, through `groq-sdk` and every key) and OpenAI. For Groq only the pages its searches returned (`executed_tools[].search_results.results`) count as sources; URLs written into the text don't. The open-source model can't search and is skipped. A provider that fails or finds fewer than `minSources` hands over to the next (`onFallback`); the last one's thin result is an error.
  - Both providers take a list of passes (`groqPasses`, `openAIPasses`) that run in parallel and are merged; failed passes are skipped. Trending runs one pass per lens in the `trending-search-lenses` prompt for both; Comment Writer and Post Comment Replies give Groq a single pass, since one Groq call runs several searches of its own.
  - OpenAI uses Responses `tools.webSearch()`, running parallel passes with `tool_choice: "required"`.
- **Humanization (`services/humanizer.ts`, `humanizeTexts`) is the last step of all 8 tools, and of Message Rewriter.** Each tool passes its final, already-verified texts (note, message, InMail subject + message, reply, comment, Trending hooks + bodies) through the user's saved **Humanization** prompt from Global AI Prompts (prompt `global-humanization`, `{{text}}` = the drafts), under the fixed rules in the `humanizer-system` prompt.
  - One structured call per result, each text as a `<draft id=… kind=… max_chars=… one_line=… rule=…>`. Code judges every rewrite on its own: same numbers, links, hashtags and @mentions; no new sender claim or placeholder; within `maxChars`/one line; plus the tool's own `validate(id, text)` (comment checks, conversation-reply problem checks, post-reply experience claims, Trending word limits).
  - Failed texts get one targeted retry told exactly what broke (the backup provider takes over if that still fails); a text that never passes keeps its verified draft. Every tool logs `humanized`. New tools must humanize their output too.
  - **Human style (strict), all 8 tools:** no em/en dashes as pauses, no colons or semicolons, no AI words (seamless, robust, leverage, delve, elevate, unlock…). Every writing prompt (each tone/tune/type/style prompt, each `*-system`, `trending-topics`, `trending-synthesis`, `global-humanization`, `humanizer-system`) ends with a `HUMAN STYLE (STRICT, NEVER BREAK THIS)` block; keep it on new or rewritten prompts. Lead-signals, About Me, Rafay Profile Info and research prompts don't have it (not written copy). In code, `lib/humanStyle.ts` (`applyHumanStyle`) rewrites every draft and rewrite inside `humanizeTexts` (links, hashtags, @mentions, times, ratios, hyphens and number ranges are kept; single-line fields such as InMail subjects get a comma instead of a new sentence), and a rewrite that adds a word from `findAiWords` is sent back.
  - Prompt Creator and Client Messaging are the exceptions: they write prompts for other AI tools and formal client updates, so their output is not humanized. Message Rewriter does humanize, because what it produces is a message the user sends as their own.
  - Global AI Prompts page: `/global-prompts` (`constants/globalPrompts.ts`, `services/globalPrompts.ts`); Rafay Profile Info is Abdul's facts source for Post Comment Replies (with About Me).

## Architecture

### Page pattern
Each tool route has two parts:
- A thin server `page.tsx` that holds only metadata and JSON-LD.
- A `"use client"` `*Client.tsx` that composes `Sidebar` and `Header` from `src/components/ui/`. Sidebar collapse state comes from `hooks/useSidebarCollapse` (localStorage key `isSidebarCollapsed`; Ctrl/⌘+B toggles it on desktop).
  - **Sidebar search:** a small "Search tools" box between the brand row and the list, outside the scrolling `nav`, so it never moves when the tools scroll. Typing filters by name as you type (every word must appear, any order, any case): a tool whose name matches stays with all its pages, a dropdown whose tool name doesn't match stays only for the pages whose names do, dropdowns that match are shown open without changing their saved state, headings with nothing left disappear, Global AI Prompts hides unless it matches, and "No tool matches" shows when nothing does. Enter opens the first match, Escape or the clear button empties it. It is hidden on the collapsed desktop rail, where Ctrl/⌘+K opens the switcher.
  - **Sidebar scroll stays where the user left it.** Every page mounts its own `Sidebar`, which used to put the list back at the top on every click. The list's scroll position is saved to the tab's `sessionStorage` (`linkpilot:sidebarScroll`, once per frame while scrolling, never while a search has shortened the list) and restored in a layout effect before paint, then once more on the next frame in case remembered dropdowns opened late. Nothing scrolls the sidebar to the active tool.
  - **Sidebar:** brand row (`SITE_LOGO_PNG` mark + "LinkPilot" + AI pill) as tall as the header; tools listed under the four `TOOL_GROUPS` headings (each tool's `group` in `constants/linkedinTools.ts`; the headings are small capitals in bold, each a button on a soft `surface-container-low` band with an arrow, so they read as section labels rather than faint captions); Global AI Prompts pinned at the bottom. **A row is one line, the tool's name only:** with 19 tools a second line of description per row is noise, so the description is the row's `title` tooltip, the rail tooltip when collapsed, and the second line in the switcher. The list stays short enough to scan at a glance (rows use 24px icon tiles, pages inside a dropdown 20px): on a 900px screen it fits with one dropdown open, and an admin with Administration open scrolls about 40px, which is deliberate rather than a regression. The search box above the list and the remembered scroll position are how a longer list is handled, so don't shrink the rows or drop a heading to win those pixels back; a new group, or several dropdowns' worth of pages, is worth re-measuring. The current tool gets a filled icon tile and a left accent bar. Each group is a `<section>` labelled by its `<h2>` heading. Collapsed on desktop it's a 76px icon rail with a custom tooltip (name + description or activity), with a hairline in place of each heading; the mobile drawer (`z-[45]`) always shows the full list. No per-link "open in new tab" arrow.
  - **Sections open and close on their own** (`TOOL_GROUPS` order, the owner's: Prompts, Workspace, LinkedIn Tools, Client Work): each heading is a `<button>` inside its `<h2>` with `aria-expanded` and `aria-controls` naming its list, and **any number can be open at once, all of them or none**: opening one never closes another (the owner asked for this after a one-at-a-time version). A closed section's list is `hidden`, so its tools are neither seen nor read out. Each section's choice is kept per browser in localStorage (`hooks/useSidebarSections`, key `sidebarSections`, one true or false per section; its own key, since the Client Work section and the Clients Management tool share the id `clients`), and survives pages and reloads; a section never touched is open while the page on screen is one of its tools. The rule is `isSectionOpen` / `withSectionToggled` / `parseSectionChoices` in `lib/sidebarSections.ts` (tested in `tests/sidebarSections.test.mjs`). A closed heading carries what its hidden tools would show, like a closed dropdown: the active bar and violet label when the page on screen is inside it, and any background activity. **A search shows every section with a match, open**, without changing the choices, and Enter opens the first match in heading order. **The collapsed desktop rail ignores sections**: the headings are hairlines there and every tool's icon shows.
  - **Dropdowns:** a tool with `links` (all 9 LinkedIn tools, plus Client Messaging, Prompt Creator and Message Rewriter: a create page, which is the tool itself, and its "view all" page) renders as a button with a chevron and `aria-expanded`, and its pages sit indented and one size smaller beneath it. **It never closes on its own:** only a click on its row opens or closes it, not choosing a page, going to another tool or reloading. The choice is kept per dropdown in localStorage (`hooks/useSidebarDropdowns`, key `sidebarDropdowns`); one never touched starts open while one of its pages is on screen. Closed, the row carries the active bar and any background activity of its hidden pages. In the rail its pages show as icons. A tool's `href` stays its main page, which the sitemap and manifest read. `toolPages` in `constants/linkedinTools.ts` builds the two links (Comment Writer adds a third, Profile Scheduler), and every link whose `href` differs from its tool's gets its `SEO_PAGES` entry derived from the link (`pageTitle`, non-indexable), so a new "view all" page needs no hand-written SEO entry.
  - **Header:** `SITE_PURPOSE` ("Outreach & Client Workspace", `config/site.ts`; it names the whole app, not only the LinkedIn tools, and is also the home page's title and social-card heading), the background-activity indicator and a "Jump to a tool" search (`components/ui/ToolSwitcher`, also Ctrl/⌘+K). The switcher reads `APP_TOOLS` (a tool with `links` as one entry per page, "Trending Topics: View Existing Topics") plus Global AI Prompts, shows each tool's sidebar heading beside its description, and searches the heading too, so typing "client work" finds that whole group. Last comes the account menu (`components/ui/UserMenu`: initials, then name, email, role and Sign out). No AI-status badge.
  - **Background activity (`lib/toolActivity.ts`):** result stores pass `activity: { href, statusOf }` to `createToolStore`; a run shows as a spinner on its sidebar item and "X is writing" in the header (`components/ui/ActivityIndicator`) while the user is on another page, then a dot / "X is ready" (or "didn't finish") until that tool is opened. New result stores must pass `activity` too.

### "View all" pages (every LinkedIn tool, Client Messaging, Prompt Creator, Message Rewriter)
- Each of these has a page listing everything it made: `/trending-topics/history` (page numbers, see Trending Topics), `/post-image-creator/history` (the gallery) and `/<tool>/history` for the ten text tools (the seven LinkedIn text tools plus `client-messaging` from `client_messages`, `prompt-creator` from `created_prompts` and `message-rewriter` from `rewritten_messages`).
- **The ten text tools share one page and one route.** `constants/savedOutputs.ts` (`SAVED_OUTPUT_TOOLS`) registers each one: its sidebar link titles, heading, noun, the table's title column (`titleHeading`), search placeholder and filters (the tone, tune, type or style, plus the context for Post Comment Replies, read from the tool's own option list), and `hideTexts` for Connection Note. `components/saved-outputs/SavedOutputsView` renders it and each `app/<tool>/history/page.tsx` is a thin page naming the tool. `GET /api/saved-outputs/[tool]?page=&search=&option=&context=&from=&to=` (404 for an unknown tool, 400 for a choice the tool doesn't have) reads the records `services/generationRecords.ts` already saves, through `services/savedOutputs.ts`: one reader per tool says which field holds the choice, which fields a search covers (who it was for and what was written, never the whole pasted profile), what was written (an InMail's subject and message, a reply and its strategy note, each copied on its own) and what it was written from. A filter marked `fromServer` takes its options from the records themselves (Client Messaging's clients, Message Rewriter's languages): the reader's `recordChoices` returns them in `choices` with every page, and the API accepts any short value for it. Client Messaging filters by client and channel, Prompt Creator by target and typed or spoken, Message Rewriter by language and typed or spoken. Adding a tool = a registry entry plus a reader.
- **A table, 50 to a page with page numbers** (cards on a phone). `HISTORY_PAGE_SIZE` (50, `constants/historyFilters.ts`) is enforced in the service, a page past the end comes back as the last page, and the total counts everything the filters match; the pager is the shared `components/ui/Pagination`. Columns: who or what it was for (with the author, for an admin), Details (the choices in violet, facts such as the company, "Edited by hand" or the language in grey), what was written, when, and the actions.
- **The list never carries what a record was written from**, only its label (`sourceLabel`), because a pasted profile or conversation can be tens of thousands of characters. `GET /api/saved-outputs/[tool]/[id]` returns one record with its whole `source`, and `DELETE` on the same path removes it; both check ownership with `visibleById` (another account's record, or a malformed id, is a 404). The page reads a record's source once and reuses it.
- **Deleting several at once** (`DELETE /api/saved-outputs/[tool]`, the same filters as GET, body `{ ids }` or `{ all: true }`): every row has a tick box, and the bar above the list offers **Delete N picked**; a second control beside the count offers **Delete all N matching** (all N when nothing is filtered), which reaches every page of the filters, not just the one on screen. Both always confirm first, in a dialog naming the exact count, and both are final. `deleteSavedOutputs` builds the records to delete with `matchingFilter`, the same helper `listSavedOutputs` uses, so a delete can never reach a record those filters would not have shown, and both forms stay inside `visibleTo(viewer)`, so a user only deletes their own records and an id belonging to another account matches nothing. Ticked ids are capped at one page (`HISTORY_PAGE_SIZE`). After a delete the page goes back to page 1 and reads again, because what is left may not fill the page that was on screen.
- **Row actions:** View (a dialog with every written text and the source, each with its own copy button), Copy for each written text by name ("Copy subject", "Copy message"), Copy for the source ("Copy profile", "Copy conversation", "Copy update"; the request is handed to `ClipboardItem` so a slow read doesn't lose the click's permission, like Post Image Creator), and **Delete on one click with no confirmation**, like Trending's Existing Topics: the row leaves at once, the page is read again once the server confirms, and a failed delete puts the row back and says so. A Prompt Creator prompt deleted here while its page still edits it answers "That saved prompt no longer exists."
- **Applied prompts** (Prompt Creator only, `canMarkApplied` on its `SAVED_OUTPUT_TOOLS` entry): **applying a prompt is how it is run** (see Dependencies under Prompt Creator, which is what stops a prompt being marked too early). A prompt that has been used is marked from the history with **Mark applied**, which writes `applied: true` to the same record endpoint the folders use (`PUT /api/prompt-creator/created/[id]`) and stores `appliedAt` on `created_prompts`; clicking again takes the mark off. Marking is not a change to what the prompt says, so it never sets `editedAt`. An applied row is shown on a clearly green background (the full `success-container`, the colour a ticked Daily Task uses; at 40% it read as near white and was asked to be darker) in **both** renders, the `xl` table row and the phone card, with a `success/60` border on the card, and carries a solid "Applied" tag (`bg-success`, white text) in `RecordTags`, so the mark never rests on colour alone and the tag does not disappear into the green; the applied row hovers one step deeper (`success/25`) so it cannot look broken against the ordinary hover grey; the row turns green at once and goes back if the write fails. The reader carries it as `appliedAt` (`appliedField` on the reader, `SavedOutput.appliedAt`), and the same mark and green card show in the Prompt Creator projects dialog.
- **Filing by dragging** (a tool with `folders`, so Prompt Creator only; `components/saved-outputs/FolderDrop.tsx`, ids in `lib/folderDrop.ts`, `@dnd-kit` as Daily Tasks uses it): each row has a grip handle and a checkbox. Dragging a handle picks up that record, or the whole picked set when the row dragged is one of them (dragging an unpicked row clears the picking first, as Daily Tasks does). While something travels, a sticky bar shows every folder plus "No folder" as places to drop on, each lighting up under the pointer, and the overlay says the record's name or "N prompts". A drop files each record through the same `moveRecord` the Move dialog uses, one write per record, so the counts and the folder tags follow and a folder filter reloads the page; a failure shows `moveFailed` and nothing else changes. Mouse needs 4px of movement, touch a 200ms hold (so a finger still scrolls), and the keyboard sensor plus the announcements make it usable without a pointer, with the Move dialog still there as the plain path. Picking supports Shift for a range, and a record deleted or left on another page stops counting as picked. `folderFromDropId` answers `undefined` for anything that is not a folder target, so a drop that lands elsewhere files nothing.
- **Written text:** Connection Note (`hideTexts`) starts every note hidden, with Show notes for the page and a toggle per row; every other tool shows its texts, cut to three lines when longer than `SAVED_OUTPUT_TEXT_PREVIEW_CHARS`, with Expand all and a Show all per row. Neither is remembered between visits. **Every text on show has a copy icon beside it** (`CopyIconButton`, the whole text however much is cut, a tick once copied, on the table and the phone cards), and a hidden note has **Copy note** beside Show note, so it copies without opening; opening it swaps that button for the icon.
- **Other lists load as they scroll.** `hooks/useCursorList` and `components/history/LoadMore` (cursor paging by `createdAt|_id`, `lib/listQuery.ts`, one extra row to know there is more) are still what Audit Management and User Management use; Employees reads its whole team in one answer so it can be dragged into order.
- **Filters are the same everywhere** (`components/history/HistoryFilters`: `FilterPanel`, `SearchFilter`, `SelectFilter`, `DateRangeFilters`): the search waits `HISTORY_DEBOUNCE_MS` (an emptied box counts at once), any change starts the list again, the date inputs send the viewer's own start and end of day (`lib/dayRange.ts`) and a backwards range is caught on the page and refused by the API. Query strings are validated with the shared pieces in `lib/validation/listFilters.ts`; a search is escaped plain text.

### Tool state survives switching tools (`lib/toolStore.ts`)
- Never keep a tool's inputs or results in component `useState`: leaving the page would lose them. Each tool has module-level stores made with `createToolStore(name, initial, { version, toStored })`, read with `useToolStore` (`useSyncExternalStore`): a `<tool>:form` store in its `*Client.tsx` and a `<tool>:result` store for the generation (`createGenerationRequest` in `hooks/useGenerationRequest.ts` for JSON tools; `useCommentGenerator`, `usePostCommentReplyGenerator`, `useTrendingTopicsSearch` for the streaming ones).
- Requests are never aborted on unmount, so a generation started before switching tools finishes into the store; only a newer request or Reset cancels it (and a cancelled request never writes).
- **Each browser tab keeps its own state.** Stores save to the tab's `sessionStorage` (`linkpilot:tool:<name>`) and also mirror to `localStorage` for 24h after the last change.
  - A tab always restores its own copy first, so the same tool open in several tabs never shows another tab's input or result, even after the browser reloads a background tab or the dev server hot-reloads.
  - Only a brand-new tab starts from the `localStorage` copy (the latest from any tab). Reset writes the empty state to the tab's own copy.
  - Never add `storage` event listeners or other cross-tab syncing to tool stores.
- `toStored` keeps uploaded `File`s (memory only) and unfinished requests out of storage. Bump `version` when a store's shape changes.
- Signing out clears every tool's saved state from the browser (`clearAllToolState`), so the next account to sign in there starts clean.
- Trending Topics loads the account's saved topics once per page load (a new tab or a refresh), not when a tab comes back into view.
- Every tool header has `components/ui/ResetButton` next to Update Prompt: it clears the pasted/uploaded data and the result, and keeps the chosen tone/tune/type/style/context.

Styling is Tailwind with Material-3 color tokens from `tailwind.config.ts` (`bg-surface-container`, `text-on-surface-variant`, `bg-primary-container`, …). Use those tokens, not raw colors. The app is light theme only.
- The scheme is **Signal Violet & Gold** (it replaced the original teal, blue-tinted surfaces and orange):
  - Brand violet: `primary` #5b21b6, hover `on-primary-fixed-variant` #4c1d95, selected `primary-container` #6d28d9 with `on-primary-container` #ede9fe, light tags `primary-fixed` #ddd6fe. Button hovers use `hover:bg-on-primary-fixed-variant`.
  - Gold accent (`secondary*`, amber): Hot/Warm tags, warnings, moderate score bars.
  - Green (`success`, `on-success`, `success-container`, `on-success-container`): a finished thing, currently a ticked Daily Task. It is a state colour, never a brand accent.
  - Neutrals are violet-tinted porcelain: `background` #f7f6fa (use `bg-background`, never a hex), ink `on-surface` #1c1826, `on-surface-variant` #4a4658, `outline` #686477 (keeps small labels ≥4.5:1 even on hover fills), hairline `outline-variant` #d6d2df. `shadow-sm/lg/xl` are overridden with soft ink-tinted shadows.
  - Colors outside the tokens: `globals.css` (body, selection, scrollbar), `SITE_THEME_COLOR` / `SITE_BACKGROUND_COLOR` in `config/site.ts` (manifest, viewport) and the social cards in `app/og/[slug]`.
- The logo is `public/linkpilot-mark.svg` (source and favicon) and its 512px render `public/linkpilot-mark.png`: a violet gradient tile with a white guiding star and a gold spark. Reference them only through `SITE_LOGO_SVG` / `SITE_LOGO_PNG` in `config/site.ts`.

### Responsive layout (every page)
- **Room for content** (the sidebar is a drawer below `lg`; beside it the page has 32px padding each side): about 680px at `lg` (1024), 936px at `xl` (1280) and 1192px at `2xl` (1536). A layout has to fit the width it actually gets, not the screen.
- **Tables appear only where they fit, cards below.** The saved-outputs history table (`min-w-[900px]`), Important Content (820), Audit Management (880) and User Management (900) show from `xl`; Existing Topics (1080, its Topic column keeps `min-w-[210px]`) from `2xl`. Below that the same rows are cards, `grid-cols-1` and `md:grid-cols-2` (Existing Topics stays one column). A new table picks its breakpoint from its minimum width, never `md`.
- **SavedOutputsView columns** narrow below `2xl`: the date wraps to two lines, and the actions are one column in a 190px cell (wide enough for "Copy rewritten message"), two columns in 270px from `2xl`. The table has `[overflow-wrap:anywhere]` so a long link or code token in a prompt can't widen a column; action buttons keep `whitespace-nowrap`.
- **The app header gives way on the left, never on the right** (`components/ui/Header.tsx`). Its right-hand group (the tool search and the account menu) is `shrink-0`, because nothing in it can shrink: squeezing that group pushes its contents past the edge of the page instead of narrowing them, which is how it came to overflow by 9px at 768px. What gives instead is `SITE_PURPOSE` on the left, which is `min-w-0 truncate`. The search field is also narrower between `md` and `lg` (`sm:w-60 md:w-48 lg:w-60`), where the purpose line first appears, so at tablet width the line fits whole rather than truncating. Measured at 360 to 1920 with the line forced wider than any font would make it: nothing leaves the header at any width.
- **Page headers:** every header action button has `whitespace-nowrap` in a `flex-wrap` row, so on a phone whole buttons move to the next line instead of their labels wrapping. Tool pages with several header buttons (Reset, Dummy Data, Update Prompt, Clients, Default Settings…) stack the title above the buttons until `xl` (`xl:flex-row`); pages with a single create button stay side by side from `sm`.
- **Phones:** `globals.css` sets every input, textarea, select and contenteditable to 16px below 768px, because iPhone Safari zooms the page into any field under 16px. Tap targets are at least 24px (WCAG 2.5.8): an inline text button gets padding rather than staying the height of its text.
- **Two-column tool pages** (Client Messaging, Message Rewriter, Prompt Creator) don't put `min-h-0` on the form section or the text-box block inside it: on a short laptop screen the form keeps its own height and the page scrolls, instead of the character count sliding under the next heading. Client Messaging goes further: form and result sit side by side only from `xl` (stacked below, where the side-by-side form was too narrow for its channel cards), its grid row fills the screen without `min-h-0`, and its channel cards are three across except in the narrower side-by-side form at `xl` (`grid-cols-2 sm:grid-cols-3 xl:grid-cols-2 2xl:grid-cols-3`).
- **`short:` is a short laptop window** (`(min-width: 1024px) and (max-height: 860px)`), added as a Tailwind **plugin variant**, not a `screens` entry: a raw screen switches off the `min-[…]` and `max-[…]` width variants the option grids use. A tool whose desktop layout is taller than such a window compacts itself there rather than making the user scroll: less page and card padding, smaller text-box minimums, and `compactOnShortScreens` on `RadioCardGroup`, which shows each card's label only and moves its description into the card's tooltip. Client Messaging goes further and swaps its seven channel cards for a list beside the client (`short:hidden` on the cards, `hidden short:flex` on the list), since seven cards cost about 190px. Post Comment Replies, Conversation Reply and Client Messaging all fit 1280x620 with nothing cut off; check a layout change against that size.
- **Checking a change:** load the page in headless Chrome at 360, 390, 768, 1024, 1280, 1440 and 1920 and look for sideways page scroll, anything cut off at the right edge, a box that scrolls sideways, a short button label on two lines, tap targets under 24px and fields under 16px on a phone, then look at phone, tablet and laptop screenshots. Fill the page with real records first: an empty state hides most layout problems.

### Branding, icons and link previews
- **Icons:** every icon in `public/` is generated from `linkpilot-mark.svg` by `npm run brand:icons` (`scripts/generate-brand-icons.mjs`, sharp): `favicon.ico` (16/32/48), `favicon-{16,32,48}x….png`, `favicon.png` (96), `icon-{48…512}.png`, opaque full-bleed `apple-touch-icon[-180x180].png` (iOS paints transparency black), `maskable-icon[-512x512].png` (glyph inside the 80% safe zone), `monochrome-icon.png` and `safari-pinned-tab.svg`. Rerun it whenever the mark changes; never hand-edit them. `BRAND_ICONS` in `config/site.ts` lists them for the layout and manifest.
- **Metadata:** the root layout sets `metadataBase` (`NEXT_PUBLIC_BASE_URL`), the `%s | LinkPilot AI` title template, icons, `appleWebApp` and `viewport` (theme colour). Each page's `metadata` is `pageMetadata("<slug>")` (`lib/metadata.ts`) built from its entry in `constants/seo.ts` (`SEO_PAGES`: title, description, card heading, indexable): canonical, `og:url`/title/description and its own card. A new page needs an `SEO_PAGES` entry. `TWITTER_HANDLE` (optional env) adds `twitter:site`/`creator`.
- **Link preview cards:** `app/og/[slug]/route.tsx` renders `/og/<slug>.png` (1200×630, ~130 KB, logo + page title centred for WhatsApp's square crop, Inter from `src/assets/fonts`), prerendered at build. Unknown slugs get the home card; a render failure returns the logo.
- **Manifest:** `app/manifest.ts` (`/manifest.webmanifest`; `/manifest.json` and `/site.webmanifest` rewrite to it) with any/maskable/monochrome icons and a shortcut per tool.
- **Offline screen (`public/offline.html`, `public/sw.js`, registered by `components/ui/ServiceWorkerRegistration` in the root layout, production builds only):** the manifest is `display: standalone`, so an installed app that can't reach the server used to show the browser's own bare "You're offline". A service worker now serves LinkPilot's own screen instead: the mark, the name and `SITE_PURPOSE` on the brand's violet, what happened, a **Try again** that checks with a real request (the browser's online flag can say online while nothing gets through) and says "Still offline" rather than pretending, and it reopens the page **by itself** when the connection returns (the `online` event and a check every 5 seconds). It fills the window and never scrolls, down to a 667x320 landscape phone (the tagline, then the hint, then the explanation give way to height), and respects reduced motion.
  - **`offline.html` is self-contained on purpose**: its styles, the logo (the mark's SVG inlined) and its script are all in the one file, because nothing else can be fetched while it is on screen. Never point it at a font, an image or a stylesheet.
  - **The worker handles page loads only, and only when they fail.** It precaches `/offline.html` and nothing else: every page, script, style and API call goes straight to the network as if it were not there, so a deploy is never hidden behind an old copy and no saved answer is ever shown as current. Don't grow it into a general cache without deciding that on purpose. Bump `OFFLINE_CACHE` when `offline.html` changes, so installed apps pick the new one up (the old cache is dropped on activate).
  - Both files are outside the proxy's matcher, so they load as themselves even signed out: a sign-in redirect cached as the offline page would be what an offline user saw. `sw.js` is served `no-cache` with `Service-Worker-Allowed: /`, so a new worker is found on the next visit.
  - It is not registered in `next dev`, where a worker between the page and the dev server gets in the way of hot reloading. To test it, use a production build, and make the server **really** unreachable: puppeteer's `setOfflineMode` only cuts the page's network, and the worker is its own target, so its `fetch` still succeeds and the real page is served.
- **Headers (`next.config.ts`):** no `X-Powered-By`; nosniff, Referrer-Policy, Permissions-Policy, no framing; HSTS in production only; brand icons cached for 7 days. `/` is a **307** (never a permanent redirect) to `HOME_PATH`.
- **Where the app opens (`HOME_PATH`, `constants/auth.ts`, at the owner's request Connection Note; it used to be the first tool, Trending Topics):** the root, a sign-in or sign-up with no `?next=` (and a `?next=/`), an already signed-in visit to `/login`, the logo and the error pages' way back (`HOME_HREF`), and the installed app (`start_url`; its manifest `id` stays `"/"`, which is what keeps it the same installed app) all land there. **None of them goes through `/`**: the root used to answer with a 308, and a browser keeps a permanent redirect for good and follows it without asking the server, so anything sent to `/` from a browser that had seen it would still open Trending Topics. A page to go back to (`?next=`) is still honoured. **An account a tool is turned off for is never sent back round**: `requireFeaturePage` and `requireAdminPage` send it to `homeFor(isAdmin, disabledTools)` (`lib/homePath.ts`): Connection Note when it may use it, otherwise its first tool, otherwise Global AI Prompts (`ALWAYS_OPEN_PATH`, never turned off). A fixed home that was itself turned off is what looped. `tests/homePath.test.mjs` checks the home page is a real tool and that turning off any single tool never sends the account back to it.

### Layers
- `src/app/api/<tool>/generate` and `…/prompts[/<id>]`: route handlers. They Zod-validate input and return `{ success, message, data }`. Dynamic `params` is a `Promise` and must be awaited.
  - Research-heavy tools (Trending Topics, Comment Writer, Post Comment Replies) stream Server-Sent Events via `lib/sse.ts`: `{status, text}` stages, then `COMPLETE` with the result or `ERROR`.
  - The other tools return JSON.
- `src/services/<tool>/`: generation logic per tool. Shared services:
  - `promptComposer` inserts `{{variable}}` placeholders into the template, or appends the data when the placeholder is missing, and strips data tags from untrusted input.
  - `promptStore` and `prompts` load templates from the database.
  - `senderProfile` and `senderContext` provide the About Me profile.
  - `postImage` extracts post text from screenshots.
  - `outreachPrompts` is the prompt factory for First Message and InMail.
  - `generationRecords` saves every tool's output (see Database).
- `src/constants/`: tool option lists (tones, tunes, styles), LinkedIn character limits and user-facing messages.
- `src/models/`: the Mongoose models, one per collection (see Database).

### Database (MongoDB `LinkPilot`, the only store; there are no prompt or data files)
Every collection has `createdAt` / `updatedAt` (Mongoose `timestamps`) and an explicit collection name.
- `prompts` (`models/Prompt.ts`): every prompt the app uses, one document per template. `key` is the template name (`PromptName` in `services/prompts.ts`, e.g. `connection-note-warm`, `global-humanization`, `sender-profile`), plus `tool`, `editable`, `content` (the text tools use) and `defaultContent` (the original).
  - `loadPrompt(name)` (async) reads `content`, cached 60s per server process; saving clears that key. A missing key throws `PromptTemplateMissing`. Keep prompts in this collection, never in code.
  - `getStoredPrompts(names)` returns `EditablePrompt`s (`isCustom` = content differs from the default) in one query, always fresh. `saveStoredPrompt(name, text)` only accepts `editable: true` prompts; saving the default text restores the default.
  - The 20 system prompts (`*-system`, research and analysis prompts, lenses, `conversation-reading`, `post-image-extraction`, `post-comment-reply-context-*`) are `editable: false` and change only in the database.
  - A new prompt means a new document in `prompts` plus its name in `PromptName`.
- `model_priorities` (`models/ModelPriority.ts`): the admins' provider order per module (see Accounts and roles).
- `provider_key_states` (`models/ProviderKeyState.ts`): which Groq key calls start from and which are resting, shared by every server instance, keys named by fingerprint only (see AI architecture).
- `ai_usage` (`models/AiUsage.ts`): one row per successful AI call, for budget tracking (see AI architecture), indexed `{ createdAt: -1, provider: 1 }`.
- `users` (`models/User.ts`), `login_events` (`models/LoginEvent.ts`, indexed newest first, by account and by event): accounts and the audit trail (see Accounts and roles).
- `employees` and `employee_plans` (`models/Employee.ts`): Employees Management (see its section).
- `prompt_revisions` (`models/PromptRevision.ts`): the text a prompt had before each save (`promptKey`, `content`), so an overwritten prompt can be recovered.
- `trending_searches` (`models/TrendingSearch.ts`): every search ever run (`result`, `topicCount`, `searchProvider`, `searchedAt`, `dismissedAt`). A search is never deleted, but a single topic can be, from Existing Topics: it leaves `result.topics` and `topicCount` goes down, and a search left with no topics shows nowhere.
- `dummy_data` (`models/DummyItem.ts`): Dummy Data items (`kind`, `slug` = the id, `name`, `fields`), unique on kind + slug.
- `clients` (`models/Client.ts`): the people Client Messaging writes to (`name`, `country`, `messageFormat`, `sampleMessages`).
- `meeting_plans` (`models/MeetingPlan.ts`): Meeting Planner meetings (`name`, `meetingDate` YYYY-MM-DD, `meetingTime` HH:mm, `status`, `completedAt`, `personName`, `prepEnabled`, the three preparation inputs, `prepStatus`, `prepError`, `prep`, `preparedAt`, and for a repeating meeting `seriesId`, `recurrencePattern`, `recurrenceUntil`, all null on a one-off meeting), indexed `{ meetingDate: 1, meetingTime: 1, _id: 1 }` for the calendar, `{ status: 1, meetingDate: 1 }` for the pending count and `{ seriesId: 1 }` (partial, series only). Nothing to do with the `meetings` collection, which holds transcripts.
- `meeting_vectors` (`models/MeetingVector.ts`) and `meeting_chat_messages` (`models/MeetingChatMessage.ts`): the pieces of each meeting with their vectors, and the chat held on that meeting (see Meeting Planner). `meeting_vectors` also carries the app's only vector search index.
- `daily_tasks` (`models/DailyTask.ts`): Daily Tasks (`content`, `taskDate` as YYYY-MM-DD, `position` within its day, `isCompleted`, `completedAt`), indexed `{ taskDate: -1, position: 1, createdAt: 1, _id: 1 }` for the newest-first list and the bulk cleanup, and `{ isCompleted: 1, taskDate: -1 }` for the overdue count.
- `meetings` (`models/Meeting.ts`): one meeting, with the transcript exactly as pasted (or as a recording was written out) kept apart from the analysis built from it, the editable `notes` built from the analysis (`notesEditedAt` once the user changed them), a `recording` (Mixed, `types/meetingRecording.ts`, null for a pasted meeting), plus `transcriptHash` / `analyzedHash` (which tell a stale analysis from a current one), the status and the chunk counters. Indexed `{ createdAt: -1, _id: -1 }` for the history, `{ status: 1, createdAt: -1, _id: -1 }` for the status filter and `{ title: 1 }` for the search.
- `meeting_chunks` (`models/MeetingChunk.ts`): what one part of one transcript gave up, written the moment it is read, unique on (meeting, transcript, part). This is what makes an analysis resumable and a retry cheap.
- `profile_schedules` (`models/ProfileSchedule.ts`): Comment Writer's Profile Scheduler, one person each (`profileUrl` in its one form or null, `name`, `role`, `company`, `location`, `sector`, `whyNow`, `whyNowDate`, `source`, `notes`, `types` in `PERSON_TYPES` order, `days` in week order), unique on `{ ownerId, profileUrl }` **for records with a link only** (partial index `ownerId_1_profileUrl_1_linked`), indexed `{ createdAt: -1, _id: -1 }`, `{ ownerId: 1, days: 1 }` and `{ ownerId: 1, types: 1 }`. `scripts/migrate-profile-people.mjs up|down [--dry-run]` moved it from links to people and back, renaming the first version's type ids on the way (applied 22 Sep 2026).
- `reference_content` (`models/ReferenceItem.ts`): the Reference Content library (`title`, `content` plus timestamps), indexed `{ createdAt: -1, _id: -1 }` for its cursor paging.
- `quick_notes` (`models/QuickNote.ts`): text saved in Quick Notes (`title`, optional and `""` by default, `content` as formatted text plus the timestamps), indexed `{ createdAt: -1, _id: -1 }` so newest-first stays stable when two notes share a millisecond.
- `created_prompts` (`models/CreatedPrompt.ts`): every prompt the Prompt Creator wrote (`name`, `prompt`, `target`, `request`, `requestSource`, `provider`, `editedAt`), including the user's later edits Each prompt also carries the `folderId` of the folder it is filed in, or null.
- `prompt_folders` (`models/PromptFolder.ts`): the folders Prompt Creator files its prompts in, one document per folder (`name`), indexed `{ ownerId: 1, name: 1 }`. A folder holds nothing itself, so deleting one only frees its prompts.
- One collection per tool for its outputs (`models/GenerationRecords.ts`, saved by `services/generationRecords.ts` from each generate route): `connection_notes`, `comment_writer_comments`, `post_comment_replies`, `follow_up_messages`, `first_messages`, `inmail_messages`, `conversation_replies`, `client_messages`, `rewritten_messages`.
- `post_image_settings` and `post_images` (`models/PostImage.ts`): the brand defaults (one document, found by a fixed `scope`, holding the display name, the colours and the saved photos) and one document per generated image. An image's document **copies** the settings it was made with rather than pointing at them.
- `important_files` (`models/AssetFile.ts`): what the app knows about each stored file (the name the user gave it, description, original name, content type, category, size, its S3 key and `status`). The file itself is in S3, never in Mongo. Each holds the inputs, the choice (tone/tune/type/style/context), the main text, and the full `result`. Profile and conversation tools also store `lead` { name, headline, company } (`lib/leadInfo.ts`: from the pasted profile, else the conversation's sender lines, else the analysis). A record that fails to save is logged and never fails the response. New tools must save their outputs too.
- `connectDatabase()` (`lib/db.ts`) turns a failed connection into a `UserFacingError`. Mongoose types stay flat: store nested results as `Schema.Types.Mixed` typed `unknown`, and give each schema its own `new Schema<IRecord>(…)`. Typing a Mixed field with a deep interface, or building schemas from a spread definition, makes `tsc` run out of memory.

### Accounts and roles
- **Two roles** (`constants/auth.ts`): a `user` works with, and sees, only the records their account created; an `admin` sees every account's records (including everything saved before accounts existed, which has no owner) and the admin-only features. Today the only admin-only feature is **Dummy Data** (its button is hidden from users and its routes require the admin role). Update Prompt and Global AI Prompts are available to both roles, behind nothing but the sign-in, and prompts stay shared by everyone.
- **Accounts** live in `users` (`models/User.ts`): lowercased unique email, name, a scrypt hash (`lib/passwords.ts`, format `scrypt$N$r$p$salt$hash`, never the password), role, `sessionVersion`, and the lockout counters. Five wrong passwords in a row lock the account for `LOGIN_LOCK_MINUTES` (15). A wrong email and a wrong password get the same message and take as long.
- **Creating accounts:** `node scripts/create-admin.mjs --email … --name "…"` and `node scripts/create-user.mjs …` (with `--reset` to change an existing account's name, password and role, which also signs it out everywhere). The password is typed at a hidden prompt or read from `ACCOUNT_PASSWORD`, never an argument. Both scripts and their shared `scripts/accounts.mjs` are in `.gitignore`: they write straight to the database and stay on the machine that has its credentials. `/signup` (only while `ALLOW_SIGNUP` is `"true"`) creates `user` accounts and can never create an admin.
- **Records with no account:** `node scripts/delete-unowned-records.mjs` counts, per owned collection, the records whose `ownerId` is missing or names an account that no longer exists; `--apply` writes exactly those to `backups/` as Extended JSON (git-ignored) and then deletes them by id. It only touches collections whose model has `OWNER_ID` (keep its list in step with `src/models`), never `users`, `prompts`, `prompt_revisions`, `dummy_data`, `login_events` or the shared `post_image_settings`, refuses to run with no accounts, and skips `important_files` and `post_images` rows, whose objects in S3 must go through the app.
- **Sessions:** `POST /api/auth/login` sets `lp_session`, an httpOnly, SameSite=Lax, 7-day cookie holding only the account id, its session version and the expiry, HMAC-signed with `AUTH_SECRET` (`lib/sessionToken.ts`). `POST /api/auth/logout` clears it, `GET /api/auth/me` returns the account (the page reads it once per load through `hooks/useCurrentUser`), `POST /api/auth/signup` creates one.
- **Two layers, on purpose.** `src/proxy.ts` (Next 16's middleware) only checks the cookie's signature and expiry: a signed-out page request goes to `/login?next=…` (a path inside the app only), a signed-out API call gets 401 with the `x-linkpilot-auth: required` header, and a signed-in visit to `/login` goes into the app. The icons, manifest, robots, sitemap and social cards stay public. **Authorization is in the routes:** every API route starts with `requireViewer()` (`services/auth/viewer.ts`, or `requireViewer({ role: "admin" })`), which loads the account from the database, so a deleted account or a bumped session version is refused at once. A new route must start with it too. In the browser, `lib/apiClient.ts` sends any 401 carrying that header to the sign-in page and back afterwards.
- **Admin-only area (`adminOnly` on a tool in `constants/linkedinTools.ts`):** `toolsFor(isAdmin)` is what the sidebar and the switcher list, so a user never sees it; `PUBLIC_TOOLS` (never the admin area) is what the sitemap and the manifest list; its SEO entry is not indexable. Its pages check the role on the server (`app/admin/adminPage.ts`, redirecting a user to the app) and its routes use `requireViewer({ role: "admin" })`. Today it is the **Administration** dropdown: Audit Management, User Management and AI Model Priority.
- **Audit trail (`services/auth/audit.ts`, `login_events`):** `signIn`, `signUp` and the logout route record every outcome (`sign-in`, `sign-up`, `sign-out`, `failed` for a wrong password or an unknown email, `locked`), and deleting an account records `account-deleted` with `performedBy`, the admin's email, which Audit Management shows as "by …" with the account (or only the email typed when none matched), the address (first `x-forwarded-for`) and the browser, system and device read from the User-Agent by `lib/userAgent.ts` (no library). Never a password or a session. **A program that signs in is named, not left Unknown:** a User-Agent that does not start with `Mozilla/` is matched against `CLIENTS` (Node's own `fetch()` sends just `node`, then curl, Postman, python-requests and the like) and shown as "Node.js" or "curl 8", marked Automated, and the device line (`deviceLabel`, used by `DeviceLine` on both admin pages) never reads "Unknown on Unknown": it names the browser and system, or the program alone, or says "Unknown device" once. The raw `userAgent` is stored on every event, so when the parser learns something new the stored `browser`/`os`/`device` can be re-derived from it; that was done once, when 51 test-script sign-ins read as Unknown. Scripts that sign in through the API should send a User-Agent that says what they are, or use a signed session cookie instead, so the owner's log is not filled with test sign-ins. Writing an event can never fail a sign-in. `users` also counts `loginCount` (sign-up is the first) and `failedLoginCount` for ever, apart from the lockout's `failedLogins`.
- **Audit Management (`/admin/audit`, `GET /api/admin/audit?cursor=&search=&event=&userId=&from=&to=`):** the log newest first, 50 a batch, searched (name, email, address, browser, system) and filtered by event and date in the database; the first batch also carries the summary cards (sign-ins and refusals in 24 hours, accounts active in `ACTIVE_DAYS`, events recorded). `?user=<id>` narrows the page to one account.
- **AI Model Priority (`/admin/models`, `GET /api/admin/model-priority`, `PUT`/`DELETE /api/admin/model-priority/[module]`):** first **Which model each module uses** (`components/admin/ModelMapTable`, built on the server by `services/modelMap.ts` and carried as `modelMap` on the overview): for every module, each job it runs (writing, live web research, screenshots, speech, the meeting chat's embeddings, Post Image Creator's images, and for Meeting Notes a pasted transcript, a recorded meeting without OpenAI and the recording's Groq-only transcript), the **Default** model and **Fallback 1, 2** that take over in turn, each as provider plus the model name from env, and the providers passed over with why (not configured, can't search the web or read screenshots or speech, left out here). It is worked out from what really decides it (the default order every user gets, `AI_MODULE_NEEDS`, `VOICE_MODULE_IDS`, what each provider is configured for, the env model names), so it can't drift from the app; an admin's own saved order shows on the row as "Admins (own order)" only where it changes that job, and the intro says how many Groq keys there are and which one calls start from. Model names only, never a key. A table from `xl`, cards below. Then the AI usage summary (see AI architecture), then one card per module in `AI_MODULE_IDS` (named from `APP_TOOLS`) with its providers in order, dragged (or moved with the arrow keys) through the shared `SortableList`; a move saves at once (`PUT { order }`, every provider exactly once, `ModelOrderSchema`), and **Default** (`DELETE`) goes back to the default. Each provider says whether it is configured and, per module, whether it will be skipped for that module's needs (`AI_MODULE_NEEDS`: web search, screenshots, speech). Saved in `model_priorities` (`models/ModelPriority.ts`, one document per module with `order` and `updatedBy`; saving the default order deletes it). **A saved order applies to admins' own requests only** (`resolveModelOrder`): a regular user always gets Groq first.
- **User Management (`/admin/users`, `GET /api/admin/users`, `GET /api/admin/users/[id]`):** totals (accounts, admins, active in 7 days, new in 30), then each account with its role, lock, sign-in and wrong-password counts, last sign-in and its device, records created and last activity. Opening one shows the tool-by-tool breakdown (count and last used) and its latest `RECENT_LOGINS_SHOWN` sign-in events. Activity is **read from the records the tools already save** (`services/admin/activity.ts`, one grouped query per kind of record for the whole batch, never one per account), so nothing extra is written while someone works; a new owned collection needs an entry there. The password hash and session version are never read out.
- **Deleting an account (`DELETE /api/admin/users/[id]`, `services/admin/deleteAccount.ts`, `components/admin/DeleteAccountDialog`):** a trash button on each account's row and a Delete account button in its activity view open a confirmation popup naming the account and listing what it made, tool by tool; Delete stays off until the account's email is typed (any case), and the route checks that email again (`DeleteAccountSchema`). It deletes **everything the account made**: every collection in activity's `SOURCES` (the same list the breakdown counts, so a new owned collection is removed as well as counted), the `meeting_chunks` of its meetings, and its files in S3 (Important Files, including unfinished multipart uploads, and its generated post images; the shared brand photos in `post_image_settings` are not the account's and stay), then the account itself, which ends its sessions at once. Its sign-in history stays in `login_events`, with the `account-deleted` event.
  - **Refused:** the admin's own account, the only admin, a mismatched email (all 400), a gone account (404), and an account with stored files when S3 isn't configured (409, before anything is removed).
  - **The order makes a failure safe to retry:** every check first, then the S3 objects (a storage failure leaves every record), then the records, then the account last, so an interrupted delete still lists the account and running it again finishes the job.
  - `next dev` keeps Mongoose models across hot reloads, so after `LOGIN_EVENTS` or a schema changes, restart it before trusting a new event to be written (the audit writer swallows the validation error by design).
- **Which tools the accounts may use (`constants/featureAccess.ts`, `lib/featureAccess.ts`, `services/featureSettings.ts`, `services/admin/featureAccess.ts`): two layers, the settings for every user and each account's own choices on top.**
  - **Tools for all users** (`models/FeatureSettings.ts`, collection `feature_settings`, one document with `scope: "all-users"`): the **Tools for all users** button in User Management's header opens `components/admin/FeatureDefaultsDialog`, and a line beside it says how many tools every user gets. `GET`/`PUT /api/admin/features` (admin only). With no document, every tool is on for everyone.
  - **One account's own choices** (`disabledTools` and `enabledTools` on the user): the "Tools this account can use" panel on that account's page (`components/admin/FeatureAccessPanel`, `GET`/`PUT /api/admin/users/[id]/features`). A switch changed there **wins over the setting for everyone, for that account alone**, both ways: off for it while on for everyone, or on for it while off for everyone. Such tools carry an **Own choice** tag, and **Follow all users** (`{ reset: true }`) drops them all.
  - **Only differences are stored.** A tool set on an account to what everyone gets anyway lands in neither list (`placeTools`), so the account follows everyone again; a choice that differs is kept, and **survives the setting for everyone changing afterwards**. An account with no choices of its own simply follows everyone. `effectiveDisabledTools(role, defaults, overrides)` is the one rule: what is off for everyone, less the account's `enabledTools`, plus its `disabledTools` (a tool in both counts as off, the safe mistake), and nothing for an admin.
  - **Groups and single tools.** Both panels are the same `components/admin/FeatureSwitchboard`: the sidebar's own headings, a switch per tool and one per heading. A heading's switch turns every tool under it off when they are all on, and all of them on otherwise, and says "3 of 8 on" when they differ.
  - **A change names only the tools it touches** (`{ tools, on }`, `FeatureDefaultsChangeSchema` / `FeatureAccessChangeSchema`), never a whole list, and it is **one atomic update**: `$addToSet` / `$pull` for everyone, a pipeline `$setUnion`/`$setDifference` on the user (`updatePipeline: true`). So two admins changing different tools at the same moment never undo each other, and a page holding an older copy can't overwrite a change it didn't see.
  - **It applies on the next request, and nobody is signed out:** `getViewer` reads the account and the settings for everyone side by side and works the result out afresh every time (so does sign-in), and `Viewer.disabledTools` is that result, which everything below reads.
  - **Testing it touches real users.** The database is shared, so a change for all users reaches the real non-admin accounts too while it lasts: snapshot the `all-users` document first and put it back exactly in a `finally`, and keep the window short.
  - **Three places refuse it, not one.** The sidebar and the switcher leave it out (`toolsFor(isAdmin, disabledTools)`, read through `useVisibleTools`), its pages send the account away (`app/featurePage.ts` `requireFeaturePage`, on every `page.tsx` of every tool, mirroring `admin/adminPage.ts`), and **its API answers 403** — which is the one that matters, since hiding a link is never the protection.
  - **A route does not have to name its tool.** `src/proxy.ts` puts the path on the forwarded request (`x-linkpilot-path`, replaced rather than trusted if it arrives from outside), and `requireViewer` maps it to a tool through `FEATURE_API_PATHS` and refuses the account there. So a new route under an existing tool is covered by being written. **The longest matching path wins**, the same rule pages follow, so a tool whose API sits inside another tool's folder resolves to itself: Projects owns `/api/prompt-creator/projects` although Prompt Creator owns the rest of `/api/prompt-creator`. That makes the two switches independent: with Projects off, Prompt Creator still writes prompts and its picker simply has no projects to offer (`usePromptProjects` reports the refusal and the picker stays on "No project"). `requireViewer({ feature })` names it outright where a path does not say, and `feature: null` opts out.
  - **`FEATURE_API_PATHS` is written out, not guessed from each tool's `href`**, because several do not match (`/connection-note` is served by `/api/connection-notes`) and a guess that matched nothing would leave that tool's API open. `tests/featureAccess.test.mjs` fails when **any** folder under `src/app/api` is neither claimed by a tool nor listed in `SHARED_API_PATHS`, so a new route cannot quietly escape the gate: classify it in one line or the suite says so.
  - **An admin always keeps every tool**, whatever is stored against the account (`getViewer` empties it, the service refuses to save it, and the panel says so instead of showing switches that cannot move). Otherwise an admin could turn the admin area off for themselves and leave nobody able to undo it.
  - **Nothing is deleted and nobody is signed out.** Turning a tool off hides and refuses it; what the account already made stays exactly where it is and comes back untouched when the tool is turned on again. It takes effect on that account's **next request**, because every route loads the account rather than trusting the session.
- **Ownership:** every owned collection has `ownerId` (`models/owner.ts`, the account id as a string; the records in `users`, `prompts`, `prompt_revisions`, `dummy_data` and `meeting_chunks` have none). Services take the `Viewer` and build their queries from three helpers: `visibleTo(viewer)` for reading (admin: everything; user: `ownerId`), `visibleById(viewer, id)` for one record (another account's record reads as not found, 404), and `ownedBy(viewer)` for bulk actions such as Clear All and the Daily Tasks cleanup, which never touch another account's records, not even an admin's. Every create writes `ownerId: viewer.id`. The "view all" pages never show whose a record is ("By …" was removed at the owner's request), not even to an admin. Brand defaults for Post Image Creator are one set per user (`scope: user:<id>`); admins share the set that existed before accounts (`scope: "default"`). Trending Topics shows each account its own newest search.

### Important Content (`/important-content`, not a LinkedIn tool)
- An entry is a `name` (required, one line), a `description` (optional, the saved text itself, kept exactly as typed, up to 20,000 characters) and a `type` (required, **free text**, never a fixed list), in `important_content`. Like every workspace module it belongs to the account that saved it; an admin sees everyone's, but **no row says whose it is**: the author line was taken off at the owner's request, the same way the "view all" pages dropped theirs. The answer still carries `owner`, so naming authors again needs no server change. The text is never written to a log.
- **One table** (cards on a phone): name, type badge, a preview of the description, when it was updated, and, under an **Actions** heading, Copy (the whole description, or the name when there is none), Edit and Delete. Paging is the shared `components/ui/Pagination`, so any page number goes straight to that page, like the "view all" pages. **The preview is the words only**: `toPlainText` drops the formatting marks and the line breaks are collapsed to spaces, because three clamped lines say more filled with words than left short by the newlines of a list or a code block, and it is set in the reading font (the monospace belongs in View details, where the exact characters matter). **Add New Content** and Edit share `components/important-content/ContentDialog`; the types already used are offered as suggestions (a `datalist`), but any new type can be typed. Delete always confirms.
- **Formatted descriptions:** the description is written in `components/ui/RichTextEditor` (a toolbar for bold, italic, strikethrough, three headings, bullet / numbered / checklist lists, quotes, inline code, code blocks, links and dividers; Ctrl/⌘+B, I, K and Shift+X; Enter carries a list on, Tab nests it; Write and Preview tabs) and **View details** (`ContentDetailsDialog`) shows it through `components/ui/RichTextView`. The text is stored as a small Markdown subset (`lib/richText.ts`, `parseRichText`), so plain descriptions saved before read exactly as they did, search and the API are unchanged, and Copy takes the text exactly as saved. The viewer builds React elements and never inserts HTML, and only `http(s)` and `mailto` links become links. The table preview uses `toPlainText`, so it shows the words without the marks. Reuse the editor and viewer for any other field that needs formatting.
- **The editor dialog is written on, not in Markdown** (`ContentDialog`, the shared `Modal` at `size="editor"`: up to 1240px wide, the window's height less 2rem above and below, centred, never full screen; the form and the editor fill it). `RichTextEditor` takes `visual`, which opens on **Visual** (`components/ui/VisualEditor`, a contenteditable page where bold is bold and a heading is a heading, with no `**` or `#` in sight) beside a **Markdown** tab showing the same text as marks; every other place that uses the editor is unchanged. The page and the text meet in `lib/richTextDom.ts`: `toTree` draws saved text as elements, and `toMarkdown` reads whatever the page holds back into the same Markdown subset, whether the toolbar, the browser's Enter or a paste made it. Anything it doesn't know keeps only its words, so a paste from any site brings its structure and never its markup or script, and plain pasted text is read as Markdown (what an AI chat's Copy button gives). Text typed as text that would read as formatting is written with a backslash (`\*`, `\#`, `1\.`), which `parseInline` now reads as the character itself; `parseRichText` also reads `####`–`######` as the smallest heading and `***x***` as bold italic. Formatting goes through the browser's editing commands, so Ctrl/⌘+Z keeps working; Ctrl/⌘+B and I are the browser's own, K opens the link bar, Shift+X strikes through, U does nothing (underline has no place in the text), Tab nests a list item. `tests/richTextDom.test.mjs` covers the round trip, escapes, pastes and image sources.
- **Text size, per entry:** A− and A+ in the toolbar step through `CONTENT_TEXT_SIZES` (12 to 24 px, default `DEFAULT_CONTENT_TEXT_SIZE` 14), saved as `textSize` on the entry and used by the editor, the Markdown tab and View details (`RichTextView`'s `fontSize`; its headings are sized in em now, so they grow with it and read the same as before at 14). It is optional in the API: an entry saved before sizes reads as 14, and a `PUT` without it leaves the size alone, so older callers keep working.
- **Images inside a description** (the toolbar's image button: upload from the computer, several at once, or an https address; or paste or drop one in): an image is a line `![alt](/api/important-content/images/<owner>/<file>)` (`lib/contentImages.ts`), shown only where `RichTextView` has `showImages` (Important Content), and only from that path or https (`isSafeImageSrc`; anything else stays text). `POST /api/important-content/images` takes the image itself as the body, at most `CONTENT_IMAGE_MAX_BYTES` (4 MB, under Vercel's 4.5 MB), reads the type from the bytes (PNG, JPG, WEBP) and stores it under `LinkPilot/important-content/<account>/<new id>.<ext>` (`services/importantContent/images.ts`). **It goes through the app, not straight to S3, on purpose**: the bucket's CORS rule refuses browser uploads from the live site (see Important Files), which is why Daily Tasks' images now upload through the app as well (see Task details). `GET /api/important-content/images/<owner>/<file>` answers with a redirect to a fresh signed link, for the account that uploaded it or anyone who can see an entry that names it. An image is an attachment: deleting an entry (one, several, or the account) removes the images no remaining entry names, after the records, logging a storage failure rather than failing the delete; an image taken out while editing is kept, because Undo can bring it back.
- **An edit saves itself; a new entry never does.** Editing, the dialog `PUT`s the entry `CONTENT_AUTOSAVE_DELAY_MS` (1.5 s) after typing settles, one save at a time (a change made meanwhile goes next), and says so in the footer: "Saving...", then "Auto-saved at 14:32" in green, "Changes not saved yet" while the name or type is blank, or why a save failed. Save changes still saves at once and closes; Close (Cancel becomes Close) saves anything still waiting first and stays open if that fails; leaving the page sends a waiting edit with `keepalive`. Adding, nothing is sent until Save content, so a half-written entry is never created.
- `GET /api/important-content?page=&search=&type=` returns `{ items, page, pageSize, total, totalPages, types }`: **exactly 50 to a page** (`HISTORY_PAGE_SIZE`, enforced in `services/importantContent/entries.ts`), **the one changed last first** (`updatedAt`, index `{ updatedAt: -1, _id: -1 }`, so an edit, auto-saved or not, brings an entry to the top and the page goes back to page 1 after one), with Previous/Next page numbers; a page past the end comes back as the last page. Search matches the name only (escaped plain text); the type filter matches the type exactly as saved; `types` is every type the viewer's entries use (`distinct`, alphabetical) whatever the filters. `POST` adds, `PUT`/`DELETE /api/important-content/[id]` edit and remove (another account's entry is a 404).

### Task details, subtasks, images, AI and copy (Daily Tasks and an employee's plan)
- **One set of pieces for both:** a task carries a line (up to `TASK_MAX_LENGTH` / `PLAN_ITEM_MAX_LENGTH`, **900**, raised from 300 at the owner's request), a **description** (formatted text, the Markdown subset of `lib/richText.ts`, up to `TASK_DESCRIPTION_MAX_LENGTH`, **6,000**, raised from 2,000; plain text saved before reads as itself), up to `TASK_MAX_IMAGES` (6) **images**, and **subtasks** three levels deep (`TASK_MAX_DEPTH`: task, subtask, sub-subtask). `components/tasks/TaskDetailsFields` writes them wherever a task is written (the shared visual editor, `RichTextEditor visual compact`, so bold and lists show as they read; thumbnails with remove; add by browsing, dropping or pasting; a **Write with AI** button), `components/tasks/TaskDetailsView` shows them (formatted text, thumbnails that open full size) on Daily Tasks, the plan editor, the plan history and the employee's link.
- **Backward compatible on purpose.** Every new field is optional: `images` beside the first version's one `image` (`TaskDetailsSchema`, `TaskDetailsEditSchema`; a body without `images` answers exactly as before, and `storedImagesOf` reads either), `parentTaskId` on a Daily Tasks create and `parentId` on a plan task (left out, a task of its own). A record saved before has no `images` and no parent and reads as a top-level task with its one image; its first save moves the image into `images`. Answers still carry `image` (the first of `images`).
- **The hierarchy is a flat list with parents** (`lib/taskTree.ts`: `buildTree`, `flattenTree`, `treeProblem`, `subtreeOf`, `copySubtree`, and `updateNested` / `removeNested` / `pathTo` for Daily Tasks' nested answers; `tests/taskTree.test.mjs`). Daily Tasks stores each subtask as its own document on its task's day (`parentTaskId`, indexed) and serves it nested (`subtasks` on each task); a plan keeps its tasks in one array (`parentId`), each task followed by its subtasks. **A fourth level is refused on the server**: `POST /api/daily-tasks` with a `parentTaskId` whose task is already a sub-subtask answers 400 (`TASK_ATTACHMENT_MESSAGES.tooDeep`), a parent that is gone 404; `PlanSchema` refuses a plan with a fourth level, a missing parent or a loop. The pages disable the button that would add one and say why.
- **Moving, deleting and cleanup take what is under a task along.** A Daily Tasks move is of a day's own tasks only (a subtask named in the order is a stale order, 409) and a task that changes day carries its subtasks to it; deleting one task, the picked ones or an employee removes everything under them and their images (records first, objects after). The week-old cleanup never leaves a subtask without its task, since both are on the same day. Counts ("x of y done") are of a day's own tasks; the overdue badge counts every open task.
- **A ticked task goes to the end of its own list** (`completedLast` / `completedLastNested` in `lib/taskTree.ts`), so finishing one sends it down without a drag and unticking brings it back where it was: only ticked and unticked change places, a task takes its subtasks along, and the subtasks of one task are sorted among themselves. It is applied where the tasks are read (`groupByDay` for Daily Tasks, `toItems` and the link's own order for a plan) **and** on the page the moment a box is ticked, so the row moves at once rather than at the next load.
- **The details are folded away until they are asked for.** `TaskDetailsView` (Daily Tasks, the plan history, the employee's link) shows a **Details (description, 2 images)** button and opens on a click, and `TaskDetailsFields` (wherever a task is written, so the plan editor too) is closed even on a task that already carries something, saying **Show details** instead of Add details. Only `TaskEditorDialog`, whose whole subject is the details, passes `alwaysOpen`. Nothing is remembered between visits, so a list always opens as a list of lines.
- **Copy is two buttons, on both modules.** The **copy icon** (`components/tasks/CopyTaskText`) puts the task's own line on the clipboard, to paste anywhere, and makes nothing; the **duplicate icon** (`CopyPlus`) is what the copy icon used to do. Every press stops at the button, since a daily task's whole row is the drag area and a click on it ticks the task.
- **Copy** (`POST /api/daily-tasks/[id]/copy`, idempotent; the plan editor copies in the page with `copySubtree`): the line, description, images and subtasks in the same shape, straight after the original under the same parent, **all open** (ticks and reasons are work done on the original, not copied). Daily Tasks copies each image object (`copyObject`, `copyTaskImages`), so deleting either task never takes the other's; a plan's copy shares the image ids, which is safe because a plan image only goes when no task in the plan or its days names it.
- **Images go through the app** (`POST /api/task-images` with the image itself as the body, at most 4 MB, the type read from the bytes, answering `{ assetId, contentType, url }`; `lib/taskImageUpload.ts`), because the bucket refuses browser uploads from the live site. The old JSON `{ contentType, size }` request for a signed PUT link still answers for any caller written before.
- **Overdue tasks come to today from a button** (`POST /api/daily-tasks/move-overdue { today, ids? }`, `moveOverdueToToday`): every task on an earlier day that still has open work, with everything under it, added to the end of today in the order the days had them, which is exactly what a drag across days writes (the day on the task and its subtasks, then the day's positions). A task whose work is all ticked stays where it is, and one open subtask brings its whole task along. Without `ids` it is every overdue task, from **Move N overdue tasks to today** beside the overdue count in the header; with them it is the tasks named, from the calendar button that shows on an overdue row. A repeat moves nothing, so the browser may safely send it again (`{ retry: true }`).
- **Writing details with AI** (`services/dailyTasks/writeDetails.ts`, the fixed `task-details-system` prompt, one short line on what done looks like and three to seven steps, nothing invented): `POST /api/daily-tasks/generate` and `POST /api/employees/generate` `{ title, parents?, description? }` answer `{ details, provider, providers }` and save nothing; the page puts the text in the editor. `PUT /api/daily-tasks/[id]` also takes `generateAI: true`, which writes the description from the task's line and the tasks above it and saves it. Both run through `runAiRequest` as the AI modules `daily-tasks` and `employees` (in `AI_MODULE_IDS`, so AI Model Priority and the usage table cover them); `lib/taskDetailsAi.ts` is the page side.
- **Daily Tasks edits in `TaskEditorDialog`** (the old details popup is gone): the line, the details and the subtasks (tick, open, add a sub-subtask, copy, delete, and a field to add one more, replaced by a line saying so on a sub-subtask), with a breadcrumb to the tasks above. **It saves itself** one second after typing settles (`PUT /api/daily-tasks/[id]` with `{ content, description, images }`), one save at a time, never while an image is uploading, and the footer says "Saving..." then "Saved at 14:32"; Save and Close save anything waiting first and stay open if that fails. The list shows each task's subtasks indented under it with a fold (`SubtaskTree`, which is not part of the row's drag area), and every row has details, **Add subtask** (disabled on a sub-subtask), **Copy task** and delete.
- **The plan editor edits inline**, since only its handle drags: every task, at every level, has **Add subtask** / **Add sub-subtask** (disabled at the third level), copy, delete and its details; subtasks sit indented under their task and fold away, and only the top level is dragged (a task takes its subtasks along). It saves itself as before (`PLAN_SAVE_DELAY_MS`). Choosing an image now saves it: the old editor never kept a file chosen there. The employee's link and the history show the same shape; a reorder on the link sends each task followed by its subtasks, and `inLinkOrder` keeps every subtask under its task whatever order it is given.
- `tests/taskSubtasks.test.mjs` covers the schemas (depth, parents, images old and new, the AI flag and request), the move-overdue body and the raised limits; `tests/taskTree.test.mjs` covers the tree helpers and the ticked-last rule in both shapes.

### Employees Management (`/employees`, not a LinkedIn tool)
- An employee is a name, city, role, date of joining (a plain YYYY-MM-DD, like Daily Tasks) and a status (`active` or `inactive`), in `employees`; like every workspace module it belongs to the account that added it (a user sees their own team, an admin everyone's, named by author). `EmployeeSchema` refuses a blank field, an impossible date or one more than a year ahead.
- **One page:** the team on the left (search over name, city and role, a status filter, active and inactive counts, the whole team at once, up to `EMPLOYEES_LIST_MAX` (500), through `useCursorList` with no next cursor) and the chosen employee on the right: details with tenure, Edit, Delete, the plan link, then the repeating daily plan and its history. Add and Edit share `components/employees/EmployeeDialog`; Delete always confirms and deletes the employee's plans with them.
- **The first employee is open on every load.** The page shows `selected ?? list.items[0]`, so a fresh load, a refresh or deleting the open employee opens whoever is first, without a click and without scrolling. The first drag pins whoever is open, so moving someone to the top never switches the details to them.
- **The team is put in order by dragging**, with the same `components/ui/SortableList` handle as the plan (mouse, touch, arrow keys). Each employee has a `position` (index `{ position: 1, createdAt: -1, _id: -1 }`); the list reads by it, ties (employees from before positions) newest first, and a new employee goes above everyone (`position` one below the lowest). A drop shows at once and `PUT /api/employees/order { orderedIds }` saves the whole team's order in one `bulkWrite`; saves are queued so quick drags land in order, and a failed save shows why and reloads the saved order. The order must name exactly the team the viewer may see (`reorderEmployees`), else 409, so a tab that missed an added or removed employee can't scramble it. Dragging is off while a search or status filter is on, or when the team is larger than one load, with a line saying so.
- **One plan that repeats every day.** The plan is kept on the employee (`planItems` in order, `planNotes`); the manager sets it once and it shows on every day until they change it. **A new day is never empty:** each day gets its own record in `employee_plans` (`period: "daily"`, the day in `periodStart`, unique per employee per day) holding that day's copy of the tasks with that day's ticks, created from the plan the first time the day is read. The record of the day being worked on always follows the plan (`syncToday`: a task added, reworded, moved or removed shows at once, and the tasks that stay keep that day's ticks); **earlier days' records are never touched again**, so the history is what the plan and the ticks really were. An employee whose tasks were written per day before this has their latest day's tasks and notes taken over as the plan once (`planStartedAt` is null until then). Weekly and monthly records from before plans became daily are never read.
- **The day never turns over at midnight.** Which day an employee is on is their own state, `planDay` on the employee (YYYY-MM-DD, null until their first day is opened, `currentDay` in `services/employees/employees.ts`), **not** the day the clock is on. Someone still working at 1am keeps the same list in front of them, and that day moves into the history only when **they** start a new day from their link. Every service call resolves the day from `planDay` and ignores the date the browser sends, except as the day their first one opens on.
- **Starting a new day is the only thing that moves it on** (`startPublicNewDay`, `POST /api/public/plans/[token] { today, action: "start-new-day" }`): the day they finished joins the history, and the next one starts from the plan with nothing ticked. The next day is the day their browser is on, or the day after the one they finished when the calendar hasn't caught up (finishing at 11pm opens tomorrow). A day already ahead of the calendar is the one to work on, so starting again is refused with 409 (`dayAlreadyOpen`).
- **Cancelling a day is the only thing that moves it back** (`cancelPublicDay`, `POST /api/public/plans/[token] { today, action: "cancel-day" }`), which is how a new day started by mistake is undone: the day being worked on is **deleted**, its ticks with it, and the newest day before it comes back out of the history to be worked on again, keeping its own ticks and following the plan from then on like any current day. The button only shows while the history has a day to go back to, and the first day answers 409 (`noPreviousDay`). The employee's page reloads afterwards, since that day leaves the history; the manager's page follows, because the day comes from the employee's record.
- **Why a task wasn't finished** (`reason` on the day's item, `PATCH /api/public/plans/[token] { today, itemId, reason }`, with `date` for a day in the history; `ReasonSchema`, up to `PLAN_REASON_MAX_LENGTH`): the employee writes it on their link, changes it and takes it back (an empty reason removes it), on the day they are on and on any day in the history. It belongs to that day, like the tick, so a new day starts with none and the day left behind keeps its own. **Ticking a task clears its reason**, since it is now done, and a done task never shows one. PATCH tells a reason from a tick by the field the body carries, so a reason that is too long is refused as a reason. `components/employees/TaskReason` shows it in amber (`secondary-fixed` / `on-secondary-fixed-variant`, the colour this app uses for attention) under the task, with "Not done: " in front; it is the one place this is rendered, and it takes the buttons to change it only where `onSave` is passed. The employee's link passes it for the day and for the history; the manager's page and the history in it show the same words without them, since only the employee writes them.
- **Every plan call still names the browser's `today`** (`TodaySchema`, at most `PLAN_TODAY_DRIFT_DAYS` from the server's UTC day), which is what opens a first day and what a new day is measured against: `GET /api/employees/[id]/plans?today=`, `PUT { today, items, notes }` (replaces the plan), `PATCH { today, itemId, done }` (a tick on the day they are on) and `PATCH { today, date, itemId, done }` (a tick on a day in the history).
- **The manager's editor (`components/employees/PlanEditor`):** the day the employee is on (which the answer carries as `date`, so the manager sees the same day they have open, with a line saying so when it is behind the calendar) and its progress, the tasks with drag handles, checkboxes, in-place wording and remove, then Add and notes; the wording, the order and the notes save themselves after `PLAN_SAVE_DELAY_MS` (a change still waiting is saved when the employee changes or the page closes, and coming back to the tab reloads the plan, picking up a day the employee has started, unless an edit is waiting). **A tick is its own atomic update** that records `completedAt`; ticking an already ticked task keeps its first time, unticking clears it. `PUT` **never takes ticks from the page**, so the manager typing can't undo a tick made from the employee's link.
- **Drag and drop (`components/ui/SortableList`, no library, the manager's editor and the link; which order a drag changes is above):** a grip handle on each row starts a drag with a mouse, a finger or a pen (pointer events with pointer capture and `touch-action: none`, so it works on phones); the other rows slide out of the way, the page or the scrolling panel scrolls itself near the edges, and the handle also moves a row with the up and down arrow keys, keeping focus and announcing the move. Used by the manager's editor and the employee's link.
  - **`multiSelect` moves several rows in one drag**, the way Daily Tasks does: a pick circle beside each handle, a Shift click for a run, one line above the list saying so, and a "N picked / Clear" chip. Dragging a picked row takes every picked row, which land together where it was dropped in the order they had (the rest fade and the dragged row carries a "+N more" badge); dragging a row nobody picked moves that one and drops the picking. The arrow keys move a group too, and the picking clears once they land. **It is opt-in and off by default**, so every list that had one-at-a-time dragging still behaves exactly as it did: it is on for the team, the plan editor's tasks and the plan link's tasks, and deliberately off for AI Model Priority, the conversation stages and the projects, where the list is short and fixed and a circle per row is clutter. `itemNoun` names the rows in the hint and the announcements.
  - **The ordering itself is `lib/reorder.ts`** (`move`, `moveMany`), kept out of the component so it can be reasoned about and tested on its own (`tests/sortableList.test.mjs`, including that nothing is ever lost or duplicated and that a picked group always lands together). **A range pick reads both its ends before calling `setSelected`**, never inside the updater: React runs an updater after the handler has returned, by which time the "last picked" ref is already the row just clicked, so a Shift click could only ever pick one row. Daily Tasks had the same bug and the same fix.
- **History (`components/employees/PlanHistory`, shared by both pages):** the days before the one being worked on that have a record, newest first, `PLAN_HISTORY_DAYS` (14) at a time (`GET /api/employees/[id]/plans/history?before=`), each with "x of y done" and when each task was ticked. **A day here is never closed for ticking**: given an `onTick`, every task in it has its own checkbox, on the link and on the manager's page, so work finished after midnight or after the day was handed in is still ticked off on the day it belongs to. Ticking a day in the history never brings it in line with the plan, so a day gone by keeps the tasks it really had.
- **The employee's link (`lib/planLink.ts`, `components/employees/PlanLinkPanel`):** `POST /api/employees/[id]/plan-link { action: "create" | "replace" | "disable" }`. The token is `<employeeId>.<HMAC-SHA256(AUTH_SECRET, id + planLinkVersion)>`, so nothing secret is stored; **New link** bumps `planLinkVersion` (every earlier link stops), **Turn off** clears `planLinkActive`, and turning it on again makes a new link. Changing `AUTH_SECRET` stops every link. An inactive employee's link doesn't open.
- **`/plan/<token>` (no sign-in; `src/proxy.ts` lets `/plan/` and `/api/public/` through, and the route checks the signature):** the employee's name and role, the tasks of the day they are on, to tick, untick and **drag into a new order for themselves** (`PUT { today, order }`: the same tasks, each once; anything else is a 409 and the page reloads), **Reset day** (clears that day's ticks, keeps the tasks and puts them back in the plan's order; earlier days are never touched; shown while anything is ticked or the order is the employee's own), **Start new day** (behind a confirmation naming the day and what is still unticked), **Cancel this day** (a red confirmation saying the day and its ticks go and naming the day they come back to, shown only when the history has one), and the history, which stays tickable. When their day is behind the calendar the page says so and heads the list "Your day" instead of "Today", so nothing rushes them into the next one.
- **Two orders, on purpose.** The manager's drag changes the plan (`planItems`), for the manager, today's record, the history of later days and the link. The employee's drag changes only `linkOrder` on the employee: their link shows it through a refresh and on later days, the plan and the manager's page never see it, and Reset today empties it. `inLinkOrder` (`services/employees/employees.ts`) lays today's tasks out in that order; a task the manager adds later goes right after the task it follows in the plan, and a removed one drops out. The link's answers carry `ownOrder` so the page knows Reset has an order to undo. It shows **only** the name, role, tasks and ticks: never the city, joining date, notes, owner or any id of the account. It cannot add, reword or delete a task, on any day: `GET/PATCH/POST /api/public/plans/[token]` take the browser's `today` (at most `PLAN_TODAY_DRIFT_DAYS` from the server's UTC day) and change ticks only. Every refusal about the link reads the same, answers are `no-store`, and the page is `noindex` with `referrer: no-referrer`.

### Lead Signals (Follow-Up Message, Conversation Reply)

### Connection Note
- **Tones** are `CONNECTION_NOTE_TONES` (`constants/connectionNote.ts`), which drives the tone cards, the API's validation, the Update Prompt tabs and the "view all" filter, each with its own `connection-note-<id>` prompt. The cards are two a row, three where the form is wide enough (`sm` stacked and from `xl` beside the result; two at `lg`, where the form column is narrow), with the full description as each card's tooltip.
- **Post Interaction** (`post-interaction`) and **Comment Interaction** (`comment-interaction`) thank someone who engaged with one of your posts, or with one of your comments, opening with their first name ("Sara thank you for interacting with my recent comment...") and one slight personal touch from their profile; they carry the same two names First Message uses. Neither the post nor the comment is ever known, so the prompts forbid naming or guessing its topic, and Comment Interaction never guesses whether they liked or replied; they sell nothing and ask for nothing, and use no company field or sender profile. Their prompts were added by `node scripts/add-thanks-tones.mjs` (the same script adds First Message's two thank-you tones), which only inserts a missing prompt; `--down` removes them again and refuses one edited in the app unless `--force`. Run it wherever the database lacks them **before** a deploy, or choosing either tone fails with the prompt missing.
- **Comment Interaction was called Post Comment (`post-comment`)** when it shipped. `RENAMED_CONNECTION_NOTE_TONES` maps the old id to the new one, and both Connection Note routes validate the tone through `idWithRenamesSchema` (`lib/validation/renamedIds.ts`, which Comment Writer's `commentTuneSchema` uses too), so a browser that remembered Post Comment, or an old request, writes and saves a Comment Interaction note. The same script renames the prompt document (`RENAMES`: the old text kept as a revision and as `renamedFrom`, its revisions moved) and moves saved notes, marking each; renames run first in both directions, so `--down` gives the old prompt its key and text back before it removes the new prompts. `tests/connectionNoteTones.test.mjs` covers the order, the rename and the schema.
- A tone prompt that places `{{sender_profile}}` gets the user's own profile (`getFullSenderProfile` in `services/senderProfile.ts`: About Me + Rafay Profile Info, also used by Post Comment Replies); other tones get nothing about the sender. Recently Funded and Hiring Startup are the defaults that use it. Their prompts start with "STEP 1. STUDY BOTH PROFILES": the model first writes `recipient_need` (what the recipient's company needs) and `my_best_match` (the user's closest project, in the profile's words) via `FitNoteSchema`, then the note around that match; both fields are logged with "Connection note generated". Tones without `{{sender_profile}}` keep the note-only `NoteSchema`.
- A link may appear in a note only when the tone prompt itself gives it (Recently Funded and Hiring Startup give the portfolio, https://rafaydev.vercel.app): a note that adds another link, or leaves out the given one, is rewritten.
- **Company tones** (`COMPANY_TONES` in `constants/connectionNote.ts`: Recently Funded = funding, Hiring Startup = hiring):
  - The page shows a Company name field (`companyName` in the form store and the API, max 100), placed in the prompt as `{{company_name}}`.
  - A named company is taken as the one with that news even when the pasted profile doesn't mention it, so the funding or hiring check lets it through. Details (round, amount, role) still come only from the profile. The note must name the company.
  - Notes in these tones must open with "Hi" and the first name ("Hi Sara congratulations…"); code checks `OPENS_WITH_HI`. The other four tones are unchanged.
- Notes are sent from the owner's account (`SITE_AUTHOR`, Abdul Rafay): both new tone prompts say so, the name in the note is always the recipient's, and code rewrites a note that contains the owner's full name or signs off with his first name (a recipient may also be called Abdul, so a leading "Abdul" is fine).
- After the first draft, code checks the note and runs up to 2 targeted rewrites (cleanest version wins). It checks for:
  - stock openers and a comma or full stop after the name;
  - funding or hiring (including "building/growing the team") the pasted profile never mentions (`PROFILE_ONLY_NEWS`);
  - going over 300 characters;
  - figures no source contains;
  - claims about the user's work that their own profile doesn't support (`findUnsupportedUserClaims`), and invented proof;
  - the recipient's numbers claimed as the user's (any number in an "I/my" sentence must be in the user's own words: their profile or the tone prompt);
  - the recipient's funding or hiring news told as the user's own ("I have some big news about raising…");
  - the user's work reshaped to mirror the recipient's product: a distinctive word from their profile, absent from the user's, in a sentence about the user's work ("I have built AI scheduling systems" to a scheduling startup).
- Claims about the user's work are checked against the sender profile only (not the tone prompt, whose examples would make anything look supported). The humanized note is rejected if it has more problems than its draft, so the last rewrite can't bring any of them back.
- Last resorts: a sentence that still borrows the recipient's numbers is dropped, and a note still over 300 characters loses its shortest middle sentence that brings it under (never the opening, the closing ask or the sentence with the link).

### Trending Topics
- The brief (the `trending-topics` prompt) targets the owner's domain: web development, AI, and SaaS/MVPs for founders. Mobile apps and consumer hardware are excluded.
- **Saved topics (`services/trending/savedTopics.ts`):** `research_metadata.search_provider` is stored as a plain string, so searches saved by a provider the app no longer uses still read back (the page names an unknown one "Web search"). every search is added to `trending_searches` with its account and kept forever. Each account sees its own newest search that found topics and hasn't been dismissed (an admin also the searches from before accounts); its `result` is Zod-validated on read. A search with no topics is kept in the history but leaves the previous topics on show. `GET /api/trending-topics/saved` returns `{ result }` (the page loads it once per page load), and `DELETE` (Reset) sets `dismissedAt` on that account's searches on show, without deleting anything.
- **Existing topics (`/trending-topics/history`, `services/trending/history.ts`):** every topic every search ever found, in a table (cards on a phone), newest search first and each search's topics in rank order. `GET /api/trending-topics/history?page=&search=&category=&format=&status=&from=&to=` (signed in; a user sees their own searches, an admin everyone's; `SavedTopicsQuerySchema`) returns `{ items, page, pageSize, total, totalPages, categories }`. **Exactly `HISTORY_PAGE_SIZE` (50) per page, enforced in the service**, and paging, search and filters all run in one aggregation that unwinds `result.topics`, so nothing is read into memory whole and a filter covers the whole history. A page past the end comes back as the last page. Search is escaped plain text over title and why-trending; a category matches one whole entry of a combined label ("AI" finds "AI, SaaS", not "AI Tools"); `format=none` finds topics saved before posts had a format; status is `current` (the search on the page now), `earlier` or `dismissed`; `from`/`to` are ISO timestamps the page builds from the viewer's own start and end of day, and a backwards range is a 400. The page debounces the search 300ms, starts from page 1 on any filter change and aborts a stale request.
  - **The list shows no source.** Each row carries its LinkedIn searches instead (`linkedinSearches`, three to five, each opening that search on LinkedIn through `linkedInSearchUrl` in `constants/trending.ts`, the same link the search page uses), and an Actions column with View and Delete.
  - **A topic is named by its search and its title** (`/api/trending-topics/history/[searchId]`), never by its place in the list, because deleting one topic moves every later topic of that search up a place while titles stay put.
  - **View** opens `components/trending-topics/SavedTopicModal`: `GET …/[searchId]?title=` returns the topic in full, shown with the search page's own `TopicCard` (research details open), under a strip naming the source, when it was searched, its rank and its status. Old topics are read with `StoredTrendingTopicSchema`, which lets the three fields early searches lacked (`post_format`, `linkedin_angle`, `post_cta`) be missing; every one of the saved topics opens.
  - **Delete** removes the topic at once, with no confirmation: the row leaves the list before the server answers, the page is read again once it does, and a failure puts the row back and says why (a topic already gone counts as deleted). `DELETE …/[searchId]` with `{ title }` is one atomic pipeline update (`updatePipeline: true`) that takes the topic out of `result.topics` and lowers `topicCount`, only on a search the viewer may see (`visibleById`); another account's topic answers 404. Deleting a topic of the search on show removes it from the Trending Topics page too.
  - **Paging is numbered** (`components/ui/Pagination`): Previous, the first and last page, the current page and its neighbours, a gap for the rest, and Next. Any number goes straight to that page.
- **The post is built for reach, not for a news summary.** The rules below are enforced in prompts *and* in code, because the model drifts from every one of them:
  - `TRENDING_POST_FORMATS` (`constants/trending.ts`) holds the 6 formats (contrarian, story, playbook, numbers, myth, prediction). The synthesis prompt assigns one per rank and `finalize.ts` guarantees the published set never repeats one, so six posts never read alike. A topic whose format had to be changed is listed in `reshape` and its body is rebuilt into the new shape.
  - **No link anywhere in the post**, and none in its first comment either: LinkedIn shows a post carrying an external link to far fewer people. `composeTrendingPost` assembles hook, body, closing line and hashtags only, and the source stays beside the post in the app.
  - `POST_TARGET_MIN_CHARS`–`POST_TARGET_MAX_CHARS` (1200–2000) is the length that travels, the hook is one line of at most `POST_HOOK_MAX_WORDS` (12) words, at most one hook in the set is a question, and the post ends on one specific question, because comments are what carry it outside the network. 3 to 5 hashtags, at the end only.
  - `services/trending/expand.ts` is the repair step. It rewrites **one post per call, a few in parallel** (asked for six long bodies at once, a model writes six short ones), for any post that is short, ends on a generic question, repeats another hook's opening word, carries an AI word or a stock phrase, talks about LinkedIn itself, or needs its format rebuilt. A rewrite is kept only when it is measurably better. It runs before the humanizer and again after it, because rewriting for tone can shorten a post or bring a stock phrase back.
  - The synthesis step is asked for `TRENDING_CANDIDATE_COUNT` (6 + 2 spares) so that a duplicate or an unverifiable source no longer leaves the page short, and `TRENDING_TOPIC_COUNT` (6) still caps what is published.
- Verification is deliberately strict and the notice says what it dropped: a reference URL must be one the live search returned (matched by page, not by spelling), and `lib/eventDate.ts` accepts an event date only when the research text or a source URL states it. Topics whose hook or body still contain a `[placeholder]` are rejected.


### Client Voices (`/client-voices`, not a LinkedIn tool)
- The voice messages a client sends on WhatsApp or Slack, in one batch of up to `VOICE_BATCH_MAX` (15). Each one comes back as its own English transcript, in the order it was added, and the batch comes down to **one** list of what the client asked for, never one list per voice.
- **The client decides what is kept.** A small picker in the page header, beside Clear batch and Update Prompt, lists the clients Client Tasks Messaging already keeps (`GET /api/client-messaging/clients`) and shows only the one chosen ("No client" for none); what the choice means is its tooltip and its screen-reader description rather than a line on the page. On a phone it takes its own line, so the name is never squeezed out by the buttons.
  - **The choice is kept on the account** (`clientVoicesClientId` on `users`, `services/clientVoices/clientChoice.ts`, `GET/PUT /api/client-voices/client` with `ClientChoiceSchema`), so the page opens on it again in any browser until it is changed. Only one of the account's own clients can be kept (another id is a 404 and the kept choice is left alone), and a client deleted since reads as none. The browser keeps a copy in `localStorage` (`CLIENT_CHOICE_KEY`) only so the page can show it before the account answers: **the account's choice wins**, and a browser copy is handed to the account only when the account has none, so a choice made before the account remembered it is not lost. A change shows at once and is saved in the background; a save that fails says so and leaves the choice on the page.
  - **With no client chosen, nothing is stored**, exactly as before: the audio goes from the browser to the transcription provider as the body of its own request, the transcripts live in the page, and closing the page deletes the batch.
  - **With a client chosen, the batch is kept with that client.** Each voice, as soon as it is written out, is posted to `POST /api/client-voices/records` (multipart: the audio, the client, the position, the name, the transcript and which provider wrote it), and the task list the batch produces is saved with it. Keeping a voice can never cost a transcript: it runs after the transcript is on the page, and a failure only shows a notice.
- **S3 holds the recordings, Mongo holds what the app knows about them**, the same split as Important Files. `services/clientVoices/records.ts` is the only place that writes either: the record is created first, the object goes to `LinkPilot/client-voices/<record id>-<clean name>` (`VOICE_STORAGE_PREFIX`, the key always built on the server), and a failed upload deletes the record, so nothing ever points at a recording that was never stored. Deleting takes the object first and the record second. Without S3 configured, saving says so and transcription carries on.
- **Two collections, both scoped to the account** (`visibleTo` / `visibleById` / `ownedBy`, so another account's voice reads as a 404): `client_voices` (`models/ClientVoice.ts`: the client, the position, the name, size and type, the storage key, the transcript, who wrote it and the task group it belongs to) and `client_voice_tasks` (`models/ClientVoiceTasks.ts`: the list as written, the voices it was made from, the voices it was made without, and when the user last edited it). Saving a task list stamps `taskGroupId` on its voices, so a kept voice can always show the tasks it belongs to.
- **The page does not list the saved voices.** It used to show them in a third column (`SavedVoicesPanel`, removed at the owner's request, to keep the page to the batch in hand), so a voice kept with a client is saved with its transcript and tasks exactly as before but is not shown anywhere in the app today. The routes that read them are unchanged and still work: `GET /api/client-voices/records` (a page at a time, `SAVED_VOICES_PAGE_SIZE`), `GET /api/client-voices/records/[id]/link` (a freshly signed link to play one), `DELETE /api/client-voices/records/[id]` (the object first, then the record) and `PUT /api/client-voices/tasks/[id]` (a batch's tasks, edited). Any new place that shows a client's voices should use them, and the panel in git history is the starting point.
- **One request per voice**, run `TRANSCRIBE_CONCURRENCY` (3) at a time from the browser (`lib/voiceBatch.ts`). That is what makes it work on Vercel: a function takes a 4.5 MB body, so `VOICE_MAX_BYTES` is 4 MB per voice and fifteen voices never share a request or a time limit. It also means a failure belongs to one voice, which is what lets that one be tried again while the transcripts that worked stay on screen.
- Transcription is the shared endpoint `/api/transcribe` (see Voice input). This module adds no transcription code of its own.
- **Every voice always has a state**: ready, queued, transcribing, done or failed. A failed voice keeps its place with the reason and a "Try this one again" button, the page says "8 of 8 voices written out" or "2 of 3, 1 failed", and the task list says which voices it was made without. A voice is never quietly dropped.
- **Pasting is the point.** The page listens for a paste anywhere on it and takes the audio out of the clipboard, and the Paste voice button reads the clipboard where the browser allows it. When the clipboard holds a link rather than audio, which is what several apps copy, it says so and points at dropping the file instead of pretending a voice arrived.
- `POST /api/client-voices/tasks` takes the transcripts, the numbers of the voices that failed and, when a client is chosen, that client and the ids of the voices that were kept, so the list it writes is saved against them. `services/clientVoices/tasks.ts` writes the list under the editable `client-voice-tasks` prompt and the fixed `client-voice-tasks-system` rules: one task per distinct request, a request made in several voices merged into one task carrying every voice number and every detail from all of them, a later voice that changes an earlier request replacing it, and context, thanks and what the client said they would do themselves left out. A voice number the model invents is dropped, because it would put a task against a voice the client never sent.
- Copy All Tasks copies the tasks as plain lines and nothing else, no voice labels and nothing from the page.

### Post Image Creator (`/post-image-creator`)
- **The gallery** loads 50 images a batch as it scrolls and filters by a search (post content, photo name, name on the image), shape, photo (`photo=none` for images made without one, or a pose) and date range, all in the query (`GET /api/post-images?cursor=&search=&size=&photo=&from=&to=`, `PostImagesQuerySchema`).
- Two halves. **Default Settings** (a dialog) holds the name that goes on a post, up to `MAX_BRAND_COLORS` (8) hex colours and up to `MAX_BRAND_ASSETS` (12) named photos. **New image** starts from those defaults, takes the post content, zero or one photo, a pose and a shape, and draws the picture. `/post-image-creator/history` is the gallery of everything made.
- **Drawing is `services/imageGeneration.ts`**, the only place that asks for an image. It is the OpenAI Images API on the same key as the chat models, with the model name from `OPENAI_IMAGE_MODEL` and never in code. With a photo it calls `images.edit` with that photo attached, which is what keeps the person recognisable, and asks for `input_fidelity: "high"`; a model that refuses that parameter is asked again without it rather than failing.
- **The instructions are built server side** (`services/postImages/generate.ts`): the fixed rules in the `post-image-system` prompt wrap the editable `post-image` prompt, and the runtime context (colours, name, post content, the pose's own instruction, the shape) is placed into both by name. The finished text is what the model gets **and** what is stored on the record, so an image can always be read back against the words that made it.
- **Two rules the app will not let an edit remove**: only the saved colours may be used for anything designed, while a photographed person keeps their own skin, hair and face (never recoloured to match a palette); and when no photo is attached the image contains no people at all, invented or otherwise.
- **History is a copy, not a pointer.** Each `post_images` document holds the colours, name, photo name, pose, shape, model and prompt as they were at the time. Changing the defaults afterwards, or the prompt, never rewrites an older image. A photo removed from the defaults keeps its object in S3, because images already made still name it.
- Storage is the shared `services/storage/s3.ts` under `LinkPilot/post-images/` (and `/assets/` for the brand photos). Brand photos go straight from the browser to S3 through a signed link; the generated image is made on the server and put there with `putObject`. Nothing is public: every preview and download is a short-lived signed link.
- **Nothing is written until the image exists.** The record is created after the image is stored, and a record that fails to write takes its object back out, so there is never a post with no picture or a picture nothing points at.
- Copy puts the PNG itself on the clipboard, handing the fetch to `ClipboardItem` so a megabyte of image does not outlive the click's permission, and a browser that refuses says so instead of looking as if it worked.
- **Drawing takes 35 to 130 seconds**, so `maxDuration` on the generate route is 300. That fits a Vercel Pro function; on Hobby, where the ceiling is 60 seconds, a generation with a photo will time out.

### Important Files (`/important-files`, not a LinkedIn tool)
- The images, PDFs, Word files, text files, videos and audio the user keeps to hand. Each one has a **name they choose**, which has nothing to do with the file name, and an optional description. `constants/importantFiles.ts` is the single mapping from a content type to a category (image, pdf, word, text, video, audio), and both the type filters and the server-side validation read it, so a type the app cannot place is a type it does not accept.
- **Storage is S3, and the app never carries the bytes.** `services/storage/s3.ts` is the only place the AWS credentials are read. The browser uploads straight to S3 with links signed there: one PUT under `MULTIPART_THRESHOLD_BYTES` (4 MB, which is also Vercel's request body ceiling), and a presigned multipart upload above it, in `UPLOAD_PART_BYTES` (8 MB) parts. A 500 MB video is 63 parts and never touches a serverless function.
- **Limits per category**, enforced on the server before anything is stored and again against S3 afterwards: video 500 MB, audio 200 MB, PDF and Word 100 MB, images and text 25 MB.
- **The record comes first, the file second.** `planUpload` writes the record as `status: "uploading"`, and only `finishUpload` (after `CompleteMultipartUpload` and a `HeadObject` that confirms what S3 really holds) makes it `ready`. Lists only ever show `ready`, so an interrupted upload can never look like a file you can open. A cancelled or failed upload calls `DELETE /api/important-files/uploads/[id]`, which aborts the multipart upload and drops the record.
- **The key is always built by the server** (`buildStorageKey`: the record's own id plus a cleaned file name, under `LinkPilot/important-files/`), never taken from the browser, so nothing can point an upload at another key or walk out of the prefix.
- **Nothing is public.** The bucket stays private and every preview or download is a signed link that expires in `SIGNED_URL_TTL_SECONDS` (15 minutes). A signed link names the key and the access key id, as every SigV4 URL does; the secret never leaves the server.
- **Paging, search and filters are the same shape as Reference Content**: a cursor of `createdAt|_id`, `ASSET_PAGE_SIZE` (24) capped in the service, search on the name as plain text (the pattern is escaped), and the category filter in the same query so paging keeps working inside a search.
- **Copy is offered only where it works**: the text of a text file, and a PNG through the Clipboard API. Video, audio, PDF and Word show no Copy button rather than one that fails (`canCopy` in `components/important-files/AssetGrid.tsx`).
- Editing changes the name and description only; `updateAssetMetadata` never touches the object. Deleting removes the object first and the record second, so a storage failure leaves the record rather than losing track of a stored file.
- The bucket needs a CORS rule allowing PUT, GET and HEAD from the app origin, with `ETag` exposed. Without it the browser cannot upload at all. **Checked on 18 Sep 2026: the bucket (`morality-data`, shared with another project) allows only `http://localhost:3000`, so browser uploads from the live site are refused** (a preflight from `https://linkedinpilot-ai.vercel.app` answers 403). The app's credentials can't read the rule (no `s3:GetBucketCORS`), and writing one replaces it whole, so adding the live origin is for whoever owns the bucket, keeping the rules already there. Meeting recordings don't depend on it: their chunks go through the app (see Recording a meeting).

### Voice input (shared)
- One recorder, one endpoint, one set of messages, used by Prompt Creator, Client Messaging, Message Rewriter and Client Voices. A new module only renders the button.
- **A recording runs up to `VOICE_MAX_SECONDS` (6 minutes)**, and the page says so: "Up to 6 minutes" beside the button, "Stop (4:12 / 6:00)" while recording, a red "30s left" warning for the last `VOICE_WARN_SECONDS`, and it stops itself at the limit and writes out what was said.
- **A long recording is never sent whole.** Vercel refuses a request body over 4.5 MB before the route runs, answering in plain text (the page used to show only "The server returned an unexpected response." past about 4 minutes 40 seconds of Chrome's default recording), and OpenAI's transcription models stop writing at 2,000 output tokens, which six minutes of Urdu can run past. So `lib/voiceParts.ts` (`splitRecording`, browser only) decodes the recording at 16 kHz mono and cuts it at the quietest quarter second between `VOICE_PART_MIN_SECONDS` (60) and `VOICE_PART_MAX_SECONDS` (100), so no word is split, and sends each part as WAV (100 seconds is 3.2 MB, under `VOICE_MAX_BYTES`, 4 MB). A recording under 100 seconds goes as it was recorded.
- `components/ui/VoiceRecorder` writes the parts out `VOICE_PART_CONCURRENCY` (2) at a time, in order, showing "Writing it out (2 of 4)", and joins them. A part that is only a pause counts as empty, not failed. **A part that fails keeps the recording**: the page names how many parts failed and offers Try again, which sends only the missing parts, so nobody has to speak for six minutes twice. Record again starts over.
- **Spoken text never fails a field for being long.** Pages add it through `appendSpokenText` (`lib/spokenText.ts`), which keeps the beginning up to the field's limit and reports how much was left out, and the page shows that as a notice (`VOICE_MESSAGES.clipped`, secondary tokens, not an error). `lib/apiClient.ts` also turns a plain-text 413 from the host into "That upload is too large for the server to accept."
- `constants/voiceInput.ts` holds every limit above, `TRANSCRIBE_ENDPOINT` and `VOICE_MESSAGES` (every microphone, recording and transcription message). Keep the wording free of any one page's subject, since all of them show it.
- `lib/audioType.ts` reads the container from the file's own bytes (wav, ogg, webm, mp4, mp3, flac), never from the browser's MIME type.
- **Which provider reads a recording follows the module.** `services/transcribeAudio.ts` (`transcribeRecording`) tries the request's order, keeping only the providers that can read speech (Groq, then OpenAI by default; `TranscriptionProvider`), skipping any that isn't configured and handing the same recording to the next when one fails or hears no speech. Every recording page renders `<VoiceRecorder transcribeFor="…">` (Client Voices sends it from `lib/voiceBatch.ts`) with its module id from `VOICE_MODULE_IDS`, sent as the `for` form field, and the route resolves that module's order for the account. The route answers `{ text, provider }`, the recorder hands `onTranscript(text, providers)` every provider that wrote a part, and a page names them with `describeProviders` (`constants/aiProviders.ts`: the first in the default order by name, any other as "(backup)"). When every provider fails, the message names each one's variable to check.
- The route answers 400 for a recording nobody can make out or one over `VOICE_MAX_BYTES`, and 503 when neither provider is configured. The microphone needs `microphone=(self)` in the `Permissions-Policy` header (`next.config.ts`).

### Message Rewriter (`/message-rewriter`, not a LinkedIn tool)
- One message in, one message out: the user types, pastes or speaks a message in any language, and gets back a short, clear English message that says what they meant, which they edit in place and copy.
- It takes its input the same way Prompt Creator does, so it reuses the same pieces rather than its own: the shared recorder (see Voice input), `MESSAGE_MAX_LENGTH`, which **is** `REQUEST_MAX_LENGTH` (12,000, room for a whole six-minute recording), and the Dummy Data kind `messages-to-rewrite`. Speaking several times adds to what is already typed.
- **One overall prompt** (`message-rewriter`, editable from Update Prompt) rewrites every message, under the fixed rules in `message-rewriter-system`. It places `{{message}}` and `{{max_chars}}`; anything it does not place is appended. The original is untrusted text inside its own delimiter tags, so an instruction written inside a message is rewritten like the rest of it, never followed.
- **Shorter is the point, meaning comes first.** `rewrittenMaxChars` caps the rewrite at the original's length, and a message under `SHORT_MESSAGE_ROOM` (280) may grow up to it, because a note such as "mtg 3pm cancel" only becomes clear as a sentence. A draft over the cap is sent back once to be cut down, and the shorter of the two wins. Nothing is added that the user did not say, and `findPlaceholders` throws out a draft with a slot the model invented.
- **The result is humanized** (`services/humanizer.ts`), like every LinkedIn tool and unlike the other two modules, with `maxChars` set just above the draft so the rewrite may reword but not grow. `humanized` is false when the humanizer's rewrite broke a check and the verified draft is what the user sees.
- `sourceLanguage` is the model's reading of the original ("Urdu"), shown on the result as "translated from ..." when it is not English.
- Inline editing is the shared `EditableOutput` + `useEditableText` pattern, so Copy always takes the edited text. Every rewrite is saved to `rewritten_messages` through `recordRewrittenMessage`, and a record that fails to save never fails the response. What the user wrote is never written to the log, only lengths, the language and the provider.

### Prompt Creator (`/prompt-creator`, not a LinkedIn tool)
- Describe a task by typing or by speaking, pick a target, and the module writes one complete English prompt for that target plus a 4 to 5 word name for it. `services/promptCreator/generate.ts` runs it through the usual `generateStructuredWithFallback` (name first, then the prompt, so the model settles the subject before writing), at a low temperature, and strips a code fence or a trailing full stop the model may add.
- **Groq first, like every module, for both jobs.** Prompts are written in the module's order and speech is read with Whisper on Groq, then OpenAI's transcription model. The page says who did each: "Speech written out by Groq" under the description (kept as `transcribedBy` in the form store, version 2, across several takes) and "Written by Groq" under the prompt (`provider` on the created prompt, from `created_prompts.provider`); a fallback reads "OpenAI (backup)".
- Targets (`constants/promptCreator.ts` `PROMPT_TARGETS`, one editable prompt each): `editor-agent` (Cursor, Claude, Antigravity: TASK, CONTEXT, STEPS, CONSTRAINTS, VALIDATE, DONE WHEN, so the agent checks its own work) and `web-search` (ChatGPT, Gemini: GOAL, SEARCH, SOURCES, ANSWER, CHECK). The description is placed at `{{request}}`, inside `task_request` tags, and is data, never instructions. Adding a target = an entry here plus its `prompt-creator-<id>` record.
- **Voice input** is the shared recorder (see Voice input). It adds what was said to the description, and `requestSource` records whether the description was typed or spoken.
- Every created prompt is saved to `created_prompts` as part of the result, because the page needs its id: the name is renamed in place and the prompt text edited in place, and both are saved back to that record through `PUT /api/prompt-creator/created/[id]` (typing settles for ~1s first). `CreatedPromptPanel` is mounted under the record id, so a new prompt starts it fresh.
- Its output is a prompt for another AI, not LinkedIn copy, so it does not run through the humanizer and its prompts carry no HUMAN STYLE block.
- Dummy Data kind `prompt-requests` (one `request` field) fills the description; Reset, Dummy Data, Projects and Update Prompt sit in the header like every tool; **Projects is a link to the Projects page**, not a popup.
- **Projects (`prompt_projects`, `models/PromptProject.ts`, `services/promptCreator/projects.ts`):** what a prompt was written for, and where its standing instructions come from. A project is a name plus an `instructions` block; a prompt points at its project through `projectId` on `created_prompts`, so deleting a project frees its prompts rather than deleting them (`deleteProject` answers how many were freed, and the Projects page says so before you confirm). **Names are unique per account without case** (`sameName`, an escaped anchored `i` regex on create and on rename, 409 `duplicate`), and the name is stored exactly as it was typed. Up to `MAX_PROJECTS` (100). Routes: `GET/POST /api/prompt-creator/projects` (POST through `withIdempotency`), `PUT/DELETE /api/prompt-creator/projects/[id]`, `GET /api/prompt-creator/projects/[id]/prompts` (that project's prompts, newest first, `PROJECT_PROMPTS_PAGE_SIZE`). Projects are **not** folders (`constants/promptFolders.ts`): a folder is where a prompt is filed, a project is what it was written for. **But every project has a folder with its name** (`folderId` on the project), so a project's prompts are filed together without anyone moving them: creating a project makes the folder (or links the viewer's folder that already has that name, whatever its case, rather than making a second), renaming the project renames its folder (unless another folder already has the new name), and **a saved prompt written in a project goes straight into that folder** (`ensureProjectFolder` in the generate route; a temporary prompt has no folder). The folder is an ordinary folder: it can be renamed, emptied or deleted, and a project whose folder is gone, or one made before folders were linked, gets one again the next time a prompt is written in it. Deleting a project keeps its folder and the prompts filed there. At `MAX_FOLDERS` the prompt is simply saved in no folder rather than failing. The picker says so under the chosen project; the Prompt Creator header no longer has a Projects button (the **Manage** link beside the picker goes to `/projects`).
- **A project's instructions end every prompt written in it**, saved or temporary: `appendInstructions` (`lib/promptInstructions.ts`, kept away from the database so it is testable on its own) adds them under an `ADDITIONAL INSTRUCTIONS` heading, and never twice. The generate route reads the project **before** calling a model, so a project deleted meanwhile answers 400 rather than wasting a call.
- **"Use this prompt once, don't save it"** (`temporary` on the generate route): the prompt is written, the project's instructions are added, and **nothing is stored** — the answer carries `id: ""`. `CreatedPromptPanel` treats an empty id as temporary: the text is still edited and copied on the page, but nothing is saved and the folder controls give way to "Not saved. Copy it before you leave this page."
- **The project picker** sits on the form with a **Manage** link to the Projects page, and the project last written for is kept in the page's own tool store (`prompt-creator:form`), so the next prompt starts in the same project; a project deleted on the Projects page (or in another tab) falls back to "No project" rather than being sent. `hooks/usePromptProjects` is the one list both read (mirroring `usePromptFolders`), with counts following a prompt created or deleted, so the picker can never offer a project the page does not show.
- **Projects have their own page, `/projects`, under Client Work right after Clients Management** (`PROJECTS_TOOL` in `constants/promptProjects.ts`, `app/projects/ProjectsClient.tsx`), laid out the way Clients Management is: the projects on the left, searched by name or instructions (`filterByWords`), the first one open on load, and the chosen one on the right with its instructions (Copy), **Write a prompt** (to Prompt Creator), **Edit** and **Delete**, then the prompts written in it. Add and Edit share `components/projects/ProjectDialog` (a name taken by another project, whatever its case, comes back as the server's `duplicate` message); Delete always confirms and says how many prompts will be kept. It moved out of the popup Prompt Creator used to manage projects in, which is gone: `components/projects/ProjectPrompts` is that popup's prompt list, unchanged (read, mark used, copy, edit through the prompt's own `PUT /api/prompt-creator/created/[id]`, delete through `DELETE /api/saved-outputs/prompt-creator/[id]`), including the full applied green (`bg-success-container` with `border-success/60`). **Nothing about the data changed**: the same `prompt_projects` documents and the same three routes, so a project made before the move is on the page as it was. `tests/promptProjects.test.mjs` covers the instructions helper and the validation.

- **Folders (Prompt Creator only; `constants/promptFolders.ts`, `services/promptCreator/folders.ts`):** a prompt sits in one folder or in none, and the folder is on the prompt (`folderId`), never a list inside the folder.
  - `GET/POST /api/prompt-creator/folders` and `PUT/DELETE /api/prompt-creator/folders/[id]`: names are tidied and unique per account whatever the case (409 on a clash), `MAX_FOLDERS` (100) and `FOLDER_NAME_MAX_LENGTH` (60) are enforced, and **deleting a folder keeps its prompts** and puts them back under "No folder", answering with how many were freed.
  - **Filing a prompt is the record's own route**, `PUT /api/prompt-creator/created/[id]` with `{ folderId }` (null takes it out of a folder). A folder the viewer may not use answers 404, and filing alone does **not** mark the prompt as edited by hand.
  - **The shared "view all" page opts in.** `SAVED_OUTPUT_TOOLS` carries an optional `folders: { endpoint, label, recordEndpoint }`, set on Prompt Creator only; `SavedOutputsView` then shows the Folder filter (a folder, **"In a folder"** for everything filed, whichever folder it is in, or "No folder"), the folder tag on each record, a Move button per record and the Folders manager, and `savedOutputs.ts` reads `folderField` on that tool's reader to filter and to name each record's folder. The three filter values are a folder's id, `IN_ANY_FOLDER` ("in-folder") and `UNFILED_FOLDER` ("none"); neither word can be mistaken for a folder, whose id is 24 hex characters, and a value nobody could have picked falls back to every prompt rather than none. **Filed is decided against the folders the viewer really has**, not against the field alone: the service reads their folders before it builds the query and matches `{ folderId: { $in: [their ids] } }` for "In a folder" and `$nin` for "No folder", so a prompt the page cannot name a folder for is filtered exactly as it is shown, under "No folder", and the two choices always add up to the whole list. The app cannot make such a prompt (filing checks the folder, deleting one frees its prompts), so it means a write that went round the app, a `folderId` saved as an ObjectId rather than a string being the one seen in practice; `warnAboutLostFolders` logs one line per page when it happens rather than letting it pass unseen. "In a folder" carries the number filed, the folder counts added up. Every other tool has no `folders`, so its page, its query and its answers are exactly as before.
  - **The Folder filter is searched, not scrolled** (`SearchableSelectFilter` in `components/history/HistoryFilters.tsx`), because a hundred folders is a long list to open: it reads as one field, and opening it gives a box to type in and the choices narrowing as you type (`matchesWords` in `lib/nameSearch.ts`, every word typed must appear, in any order and whatever the case), with the arrow keys, Enter, Escape and a click outside. It takes and gives back exactly what `SelectFilter` does, an option’s id or "" for all of them, so "All folders", "In a folder" and "No folder" are choices in the same list and the query is unchanged. Typing matches a folder’s **name** and never the count beside it (`searchText` on the option). Every other filter, on every tool, is still the plain `SelectFilter`.
  - `components/saved-outputs/MoveToFolderDialog` is the searchable picker: it filters as you type, always offers "No folder", and a name that matches nothing can be created and used in the same step. It hands back the whole folder, not just its id, so a folder just created is named on the row without waiting for the list to reload. `FoldersDialog` makes, renames and deletes folders (delete asks first and says the prompts are kept). `hooks/usePromptFolders` loads the list once per page and keeps the counts in step.
  - The create page files a prompt too: `CreatedPromptPanel` shows which folder it is in and opens the same dialog, so a new prompt goes straight into a folder.

- **Dependencies: what a prompt waits for (Prompt Creator only; `constants/promptDependencies.ts`, `lib/promptDependencies.ts`, `services/promptCreator/dependencies.ts`).** Work written as a series ("set the schema up", then "write the queries", then "write the tests") is run in order, so a prompt can say which prompts must be run before it, and it can't be ticked off before them.
  - **Running a prompt means applying it.** Nothing here executes a prompt: the user pastes it into Cursor, Claude or ChatGPT and then marks it applied, so `appliedAt` on `created_prompts` **is** the "has run" flag and there is no second one. That is the whole reason marking is what dependencies guard.
  - **The dependencies are ids on the prompt itself** (`dependencyIds`, indexed), the way a folder is, in the order they are to be worked in. A prompt saved before this has none, so **every older prompt is independent and runnable**, and an empty list makes a prompt independent again.
  - **Three states, worked out from what has run** (`dependencyState`): **independent** (waits for nothing), **ready** (waits for prompts that have all run) and **blocked** (waits for at least one that hasn't). They never overlap and cover every prompt between them, so the three filters always add up to the whole list.
  - **A dependency that was deleted is not waited for.** Deleting a prompt pulls its id out of everything that waited for it (`forgetDeletedPrompts`, from both the single and the bulk delete), exactly as deleting a folder frees the prompts in it, and any id left over from a write that went round the app counts as satisfied rather than blocking a prompt for ever. The list and the filter agree on this, which is the same rule folders follow.
  - **The filter runs in the database, over the whole list, not over the page on screen.** `blockingIds` reads the ids that are really waited on (`distinct` on `dependencyIds`, so it stays small however many prompts there are) and keeps the ones that exist and have not run; `dependencyCondition` then builds each state from that one list. Naming what each row waits for is one more query per page (`namedDependencies`), never one per row.
  - **Nothing can be marked applied while it waits.** `updateCreatedPrompt` calls `assertCanRun` before it writes anything, and the route answers **409** with a message naming the prompts to run first (`describePending`), so the refusal says what to do rather than only that it can't be done. The page checks the same rule with the same helper before it asks, so the button is already disabled and the error never comes as a surprise; the projects dialog, which also marks prompts applied, shows the server's message. **Taking the mark off is never blocked**: it says what happened, not what may happen next.
  - **Loops are refused before they are written** (`findLoop`): a prompt can't wait for itself, and it can't wait for a prompt that already waits for it, however long the chain, because every prompt in a loop would be blocked for ever. A prompt waits for at most `MAX_DEPENDENCIES` (20) others, each once.
  - **On the page** (`dependencies: { endpoint, label }` on the `SAVED_OUTPUT_TOOLS` entry, opted into the same way as `folders`): each row carries a **Ready** or **Blocked** tag (a word, never colour alone) and a "Waits for A, B" tag whose tooltip lists each one with whether it has run; the **Waits for** action opens `components/saved-outputs/DependenciesDialog.tsx`, which lists the account's prompts newest first, searched as you type, with what it already waits for shown picked (whatever folder those are in); and the filter offers Independent, Ready and Blocked. **The dialog has its own Folder choice and starts on the prompt's own folder**, because a series is filed together and what a prompt waits for nearly always sits beside it; it switches to another folder, No folder or All folders (the shared `SearchableSelectFilter`), and a prompt in no folder starts on All folders.
  - **What a prompt waits for is set on the create page too**, not only from the history: `CreatedPromptPanel` shows a "Waits for A, B" chip beside the folder and a **Set / Change what it waits for** button that opens the same dialog, starting on the folder the prompt was just filed in. It saves through the record's own `PUT` and throws on a refusal, so a loop or a prompt deleted meanwhile is explained in the dialog, which stays open. A temporary prompt has no record, so it shows neither. Marking a prompt applied updates every row waiting for it at once, so **the last dependency of a blocked prompt turns it ready without the page being read again**.
  - `GET /api/prompt-creator/created?search=&folder=&exclude=&include=` lists what a prompt may wait for (names and marks only, never the prompt texts); `folder` is a folder id, `UNFILED_FOLDER` or "" for all, and "No folder" is decided against the folders the viewer really has, the same rule as the history's folder filter, so the two never disagree about where a prompt is; and `PUT /api/prompt-creator/created/[id]` takes `dependencyIds`. Changing what a prompt waits for is not a change to what it says, so it never counts as edited by hand. `tests/promptDependencies.test.mjs` covers the states, the loop check, the tidying and the validation.

### Client Messaging (`/client-messaging`, not a LinkedIn tool)
- Each client in the `clients` collection keeps their **own** message format and exactly `SAMPLE_MESSAGE_COUNT` (2) sample messages. The samples are the shape to copy, never content to reuse; the format and the samples are what every message for that client follows.
- `components/client-messaging/ClientsModal` manages them (one tab per client, add, two-step delete, "Write to this client"). Every route here needs a signed-in account, like the rest of the app.
- **One overall prompt** (`client-message`, editable from Update Prompt) writes every message, for every client and channel, under the fixed rules in `client-message-system`. It places `{{message_format}}`, `{{sample_messages}}`, `{{update}}`, `{{channel}}` and `{{country}}`; anything it doesn't place is appended.
- **The client's name never appears in the message.** Their sample messages usually greet them by name, so the first draft often copies it: that is expected and handled, not an error.
- **Nothing is thrown away for a content problem (`services/clientMessaging/generate.ts`).** The retry chain, outermost last:
  1. `withProviderRetry` retries a provider twice on transient failures, and the module's providers take over in order (shared behaviour).
  2. A first draft that fails on **both** providers is asked for once more, because the models are random enough that a second ask usually lands; only then does the user see an error.
  3. A draft that names the client, or runs more than `LENGTH_TOLERANCE` past the channel's length, gets up to `MAX_REWRITES` (2) targeted rewrites saying exactly what to fix. The cleanest version wins, and a rewrite that makes things worse is dropped.
  4. A name that survives every rewrite is removed in code (`removeNames`), and the result carries a warning to read it once before sending.
  - A draft counts as unusable only when it is empty or invents a `[placeholder]` that appears nowhere in the client's format, samples or the update: client updates are technical, so brackets the user wrote themselves are kept (`findPlaceholders` in `lib/generatedText.ts`).
  - When every attempt fails the route answers **503**, so the browser's own retry policy (`lib/apiClient.ts`) tries again before the user sees "the AI models did not answer".
- What you want to tell the client can be **typed or spoken** (the shared recorder, see Voice input; several takes build one update) and is capped at `UPDATE_MAX_LENGTH` (12,000, the same ceiling as the other spoken fields, so a whole six-minute recording fits) in the field and in the API.
- Channels (`constants/clientMessaging.ts` `MESSAGE_CHANNELS`): LinkedIn, Upwork, Fiverr, Slack, Discord, WhatsApp and Email. Each sets the length the message is written to; only Email has a subject (`hasSubject`), and every other channel returns `subject: null`. Adding a channel = an entry here.
- Every message is saved to `client_messages` with the client it went to, and the result carries that record's id. Its output is a formal client message, not LinkedIn copy, so it does not run through the humanizer.

### Meeting Planner & Preparation (`/meeting-planner`, not a LinkedIn tool)
- The opposite end of the meetings module: this one is **before** the meeting. A meeting is a name, a day and a time; a person, and the whole of preparation, are optional. Its own collection (`meeting_plans`), its own routes and its own prompts, sharing nothing with the transcript module.
- **Days and times are plain strings** (`meetingDate` YYYY-MM-DD, `meetingTime` HH:mm) taken from the browser's clock (`lib/meetingDates.ts`, which shares `todayIso` with Daily Tasks), so a meeting never drifts a day or an hour on a server in another timezone. The routes accept a `today` at most a day from the server's UTC day.
- **The page:** today's meetings at the top (count, names, exact times, status), then a month calendar where each day shows its meetings by name and time, with "+N more" when a day is fuller than `DAY_CELL_MAX_MEETINGS`; selecting a day lists **all** of that day's meetings beside it, so nothing is ever hidden. The calendar moves a year either way (`CALENDAR_MONTH_RANGE`), one indexed month query at a time.
- **A meeting with preparation says so wherever it is listed** (`components/meeting-planner/PrepBadge`, `prepStateOf`): a filled "Prep ready" tag once it is written, "Preparing..." while it runs, "Prep failed" when it didn't finish, and nothing for a meeting without preparation, in today's list, the day panel and beside the name on the meeting's own page. Calendar cells are too small for a label, so a meeting whose preparation is written gets a spark and a ring on its chip (and "preparation ready" in its tooltip), with a one-line legend above the grid.
- **Status** is `pending` or `completed`, switched from today's list, the day panel or the meeting page, written with a small `PUT` and reflected everywhere at once.
- **Repeating meetings (a series).** The New meeting form (only when creating, `allowRepeat`) has **Repeat this meeting**: `RECURRENCE_PATTERNS` (Every day, Every weekday, Every week) and an **Until** day, defaulting to a week of days or a month of weeks and never more than `RECURRENCE_MAX_DAYS` (31) past the first meeting, so no open-ended series is ever written. The form lists the days and its button says "Save 7 meetings".
  - **A series is one ordinary meeting per day**, written in one `insertMany` by `createMeeting`, all sharing a new `seriesId` and carrying `recurrencePattern` and `recurrenceUntil`; the days come from `lib/meetingRecurrence.ts` (`recurrenceDates`, pure, shared by the page and the server). Each copies the name, time, person, link and what was pasted; **preparation is queued on the first only**, since writing it for every day would call the model once a day for the same person, and any other can switch it on from its own page. So every occurrence is moved, ticked off, prepared, chatted with and deleted like any meeting, and the calendar needs no expansion logic: the month query simply finds them.
  - `POST /api/meeting-planner` takes an optional `recurrence: { pattern, until }` (`CreateMeetingSchema`: the end on or after the first day, within the window, at least two meetings); without it the request and the answer are exactly what they were. It answers with the first meeting plus `seriesSize`. The edit route's schema never takes it, so a saved meeting is never turned into a series.
  - **Per occurrence:** the day panel has a pencil (`MoveMeetingModal`, the day and time of **this meeting only**, a plain `PUT`) and a bin. The meeting page's Edit also changes that occurrence alone and says so. **Deleting** goes through `DeleteMeetingDialog`: a one-off meeting confirms once as before, and a meeting in a series offers **Delete this meeting only** or **Delete all N meetings**. `DELETE /api/meeting-planner/[id]` deletes one, as always; `?scope=series` (`DELETE_SCOPES`) deletes every meeting of its series the viewer may see, each with its vectors and chat (`deleteSeries`), and answers the count. The meeting's own `GET` carries `seriesSize` (what is left of its series) so the dialog can name it.
  - A series shows as `SeriesBadge` ("Every week") in today's list, the day panel and the meeting page, and a small repeat mark on its calendar chips (in the legend too). `tests/meetingRecurrence.test.mjs` covers the days, weekends, month and year ends, the window and the defaults.
- **Preparation** (`services/meetingPlanner/prepare.ts`) runs only when the user asks: the meeting is saved first (`prepStatus: "queued"`), then `POST /api/meeting-planner/[id]/prepare` writes it and saves it on the meeting. Reading the meeting never regenerates it; only "Prepare again" does. A failed run leaves the meeting and any earlier preparation untouched, records why, and can be retried. `claimPrepRun` makes two runs at once impossible, and treats a run older than `STALE_PREP_MS` as gone, since a serverless function can be killed mid-run.
- **What it reads:** the lead's profile, the conversation so far and the meeting notes the user pasted, plus `getFullSenderProfile()` (About Me + Rafay Profile Info) as the user's own context. It never gets a second source, and the fixed rules in the `meeting-prep-system` prompt (not editable) stop it inventing a background for either side: observations are marked `stated` or `inferred`, what nobody knows goes to `open_questions`, and `cautions` says what the user must not claim. `findUnsupportedFigures` catches a number no source contains and asks for one rewrite.
- The prompt the user can edit is `meeting-prep-preparation` (Update Prompt on the page); it decides the read of the person, the topics and the nine stages of the conversation.
- **Ask this meeting (`/meeting-planner/[id]`, `components/meeting-planner/MeetingChatPanel`): a chat that answers from the meeting itself, through its own vectors in MongoDB.** The `meeting-chat-system` prompt keeps the answers in simple, everyday English, formatted for someone reading them quickly before a call, and words to say out loud in quotation marks on their own line.
  - **The meeting is a little vector database.** `lib/meetingChunks.ts` cuts it into pieces that each stand on their own: the details, the profile, the conversation so far, the notes, and every part of the preparation (the read of the person, each topic, each stage of the conversation plan with its steps, the projects, the deal path, the cautions). Long text is cut at a paragraph or a sentence end, `CHUNK_MAX_CHARS` (1,200) with `CHUNK_OVERLAP_CHARS` of overlap, and each piece keeps the label an answer names it by ("Stage 2. Their situation"). Nothing there talks to a model or the database, so the rules are testable on their own.
  - **`services/meetingPlanner/vectors.ts` keeps those pieces in `meeting_vectors`** (`models/MeetingVector.ts`) with the vector the embedding model wrote for each. The vector search index (`meeting_vectors_index`, created once from the app, cosine, with `meetingId` and `ownerId` as filter fields) is what makes the collection searchable. Every piece carries `sourceHash`, the fingerprint of everything the meeting held when they were written, so `syncMeetingVectors` writes again only when the meeting has actually changed (editing it, preparing it again, editing the conversation or the projects) and does nothing otherwise. New pieces are written **before** the old ones are deleted, and the write waits until the index can find them (`waitForIndexed`), so a question asked in that moment is never answered as if the meeting were empty.
  - **A question carries only what matches it.** `searchMeeting` embeds the question through LangChain's `MongoDBAtlasVectorSearch` over the same collection, pre-filtered to that meeting, and keeps the `MATCHES_PER_QUESTION` (8) nearest pieces above `MIN_MATCH_SCORE`. So the whole meeting is never sent with every question, however long the profile is.
  - **The answer is written as it arrives.** `services/meetingPlanner/chat.ts` puts the matched pieces, the last `CHAT_CONTEXT_MESSAGES` of the chat and the question under the fixed `meeting-chat-system` prompt, and streams the answer through `streamTextWithFallback` (`services/ai.ts`) in the module's provider order, so Groq writes it and OpenAI takes over only if Groq can't. `POST /api/meeting-planner/[id]/chat` streams it as Server-Sent Events (`TOKEN`, then `COMPLETE`), `GET` returns the chat and how many pieces are searchable, `DELETE` clears the chat.
  - **What the meeting can't answer is still answered.** The prompt's rule is to answer from the pieces when they hold it, and otherwise to say plainly that this isn't in the meeting notes, explain the term or the subject itself, and tie it back to this person and this call. Under each answer the page says what it was read from, or that it came from general knowledge, and which provider wrote it.
  - **The chat reads like a chat.** A question can be typed or **spoken** (the shared `VoiceRecorder`, `transcribeFor="meeting-planner"`, so Whisper on Groq writes it out and OpenAI covers it; what was said is added to whatever is already typed). An answer is shown with its formatting through the shared `RichTextView` (**bold**, *italics*, bullets and numbered steps; the model is told to use that much and nothing heavier), never as the marks around the words, and **every message has a copy button** that copies the plain text. Under an answer the page says what it was read from, or that the meeting did not hold it, and which model wrote it is the tooltip rather than another line on screen.
  - **The chat is kept with the meeting** (`meeting_chat_messages`, `models/MeetingChatMessage.ts`), so it is still there on the next visit and a follow-up ("explain that in one sentence") makes sense. **Expand** opens the same chat over the whole screen (Escape leaves it), and Clear empties the chat without touching the meeting, its preparation or its vectors. Deleting a meeting deletes its vectors and its chat with it.
  - Embeddings are OpenAI's (`OPENAI_EMBEDDING_MODEL`) because Groq has none; they are counted like every other call (`kind: "embedding"` in `ai_usage`).
- **What a preparation holds, in the order the page shows it:** `meeting_context` (decided first: `they_asked_for_a_project`, `you_reached_out` or `unclear`, because a project they brought makes every topic and stage about that project, while outreach means working out from their profile where the user fits), the read of the person, the topics, `projects_to_show` (2 to 4 of the user's own projects, named as the profile names them, with why each will land with this person), `your_intro` (first person, from the profile's positioning and numbers only, shaped to the person, with a Copy button), the conversation, winning the work and cautions. The meeting's goal is to earn the work respectfully (full time, part time or contract), never by pressure.
- **The conversation is a script** (`conversation`, `ScriptStage[]`): numbered stages, each an ordered list of steps (`SCRIPT_STEP_KINDS`): **say** (statements only), **ask** (one question), **listen** (stop talking, what to listen for), **show_project** (the project named as in `projects_to_show`, `minutes`, the `features` to show and what to say while showing it) and **note** (a private reminder). Step text may carry the rich text marks. `ConversationScript` renders it with a colour and icon per kind, so what to do reads at a glance during a call.
- **Checks after generation** (`findPlanProblems`, with invented figures, one targeted rewrite kept only when it is no worse): a question inside a say step, a stage with no ask, questions with no listen, a stage that doesn't end with a say leading on, a project not named in the profile, a show step with no features, features the profile doesn't describe for that project (`unsupportedFeatures`: each feature must share a word with the profile's own description of it, cut at the next entry, so "SMS reminders" copied from the lead's request is caught), no show step at all while there are projects to show, and a specialty in the lead's industry the profile never names. Last resorts: `moveQuestionsOutOfSpeech` turns a question left in a say into its own ask step, and `dropUnsupportedFeatures` removes invented features. A step's minutes are a number, never text, so a suggested time is not taken for a claimed figure.
- **Editing (`ConversationEditor`):** Edit on the conversation turns it into the editor: stages and the steps inside them are dragged into order with the shared `SortableList` (mouse, touch, arrow keys; nested), numbering follows, each step's kind can be changed, its text is written in `RichTextEditor` with `compact` (bold, italic, lists, links, no Write/Preview tabs), a show step edits its project (suggested from `projects_to_show`), minutes and features (one per line), and stages and steps are added and removed (a stage deletes on a second click). Collapse all makes long stages easy to reorder. The draft lives in the tool store `meeting-planner:conversation-draft`, so leaving the page or refreshing keeps unsaved edits; Ctrl/⌘+S saves, and closing the tab with unsaved changes asks first. `PUT /api/meeting-planner/[id]/conversation { stages }` (`ConversationScriptSchema`: every stage titled, ids unique, limits in `constants/meetingPlanner.ts`) replaces only `prep.conversation`, sets `prep.conversation_edited_at` and drops an old `conversation_plan`; it answers 409 while a new preparation is being written or when there is none. **Prepare again** asks first when the conversation was edited or is being edited, because it replaces it.
- **Full view (`ConversationFullView`):** the conversation alone over the whole screen (a portal at `z-[80]`), for reading during the call. **It opens straight into the browser's own full screen**, on the activation of the click that opened it; a browser that refuses leaves it filling the window. **There is no header and no width limit**: the conversation starts at the top of the screen and uses the whole width, less a small margin, so a long line stays on one line instead of wrapping. The only controls are the two text sizes (remembered in this browser) and a cross, floating faintly over the top corner, so they cost the reading area no height. **The view is the full screen, so leaving full screen closes it**, which makes one press of Escape enough; outside full screen Escape closes it too. The reading area takes focus so the keyboard scrolls it.
- **Projects to show (`ProjectsToShowPanel`):** always shown on a prepared meeting. The user adds a project (name, optional link, optional note on why or what to show), edits or removes any, and drags them into order; every change sends the whole list to `PUT /api/meeting-planner/[id]/projects { projects }` (`ProjectsToShowSchema`: a name, a link that is empty or http(s), at most `MAX_PROJECTS_TO_SHOW`; a typed link without a scheme gets `https://` from `normalizeProjectLink`), which replaces only `prep.projects_to_show` (the shared `savePrepPart`, also used by the conversation, refuses while a preparation is being written). A project the user adds or edits is `added_by_user` and shows "Added by you"; its link opens in a new tab, and every show step naming that project gets an **Open project** button (`projectLinksOf`, matched by name) on the page and in the full view. **Prepare again keeps them:** `prepareMeeting` passes them as `<projects_i_chose>` (`{{chosen_projects}}` in the preparation prompt), the rules make each one come first and get a show step, what the user wrote about a project counts as their own profile for the project and feature checks, a chosen project with no show step is a problem for the rewrite, and `mergeProjects` puts them back first with their ids, links and notes, followed by the model's other suggestions. `projectsOf` gives projects saved before this an id and an empty link.
- **Older preparations** (`conversation_plan` with what to say, questions and a transition per stage) are read as scripts by `conversationOf` (`lib/meetingScript.ts`), so they show, open in full view and can be edited; saving an edit turns them into scripts. The other new fields are optional in `types/meetingPlanner.ts` for the same reason. `tests/meetingScript.test.mjs` covers the conversion and the save validation.

### Daily Tasks (`/daily-tasks`, not a LinkedIn tool)
- A task is one line of text on one day. **The browser sends its own day** (`todayIso` in `lib/taskDates.ts`) with every read and write, so the day never turns over at the server's midnight; the routes accept a `today` at most a day from the server's UTC day and reject anything further. Days are compared as plain `YYYY-MM-DD` strings (`shiftDate`), never as timestamps.
- **Writing a day at once:** the composer holds up to `MAX_TASKS_PER_SUBMIT` rows (Enter opens the next, a pasted list fills one row per line, Ctrl/⌘+Enter saves) and `POST /api/daily-tasks` takes them as one `contents` array. Blank rows are dropped and a row repeated in the same submission is saved once, so one `insertMany` writes the day. A task may be dated today or earlier, never later, because a later day would never show in the list.
- **The list:** `GET /api/daily-tasks?today=&page=` answers page 1 with today and the six days before it, grouped by day, newest day first, each day's tasks in their `position` order (ties, from before positions existed, in the order they were written); a new task goes to the end of its day. Later pages are older days, `HISTORY_DAYS_PER_PAGE` days at a time (two indexed queries, never one per day), so the history is reachable without ever loading it all. The page number is clamped to what exists.
- **Changing a day already on the list:** each day ends with an "Add task to this day" row (Enter saves and keeps it open for the next, Escape closes) which posts one task to that day, and every task has its own delete button. A task is one line, so **it deletes on a single click with no confirmation**, the way one saved note does in Quick Notes: the row leaves at once and comes back if `DELETE /api/daily-tasks/[id]` fails (404 when it was already gone). Only the week-old cleanup confirms.
- **Drag and drop (`@dnd-kit/core`, `sortable`, `modifiers`, in `components/daily-tasks/TaskDayList`):** **the whole row is the handle.** A task is dragged from anywhere on it to another place in its day or into another day on the page. One line above the list says so, and says how to move several. Three sensors, because one pointer rule cannot suit all three: `MouseSensor` needs 4px of movement, so a click still ticks the task; `TouchSensor` needs a 200ms hold (`touch-action: manipulation`), so a finger swiping over a row still scrolls the page; `KeyboardSensor` works from the grip (focus it, Space to pick up, arrows to move, Space to drop, Escape to cancel, with spoken announcements). The grip stays as the visible sign that a row moves and as the keyboard's way in; the pick circle, the tick box and the bin each stop a drag starting from them (`stopPropagation` on `pointerdown`), and a click that only finished a drag never ticks the task (`wasDragging`, 250ms).
  - **Several tasks move together.** Every row carries a **pick circle**, always visible and needing no mode to turn on: click the circles of the tasks to move, and a Shift click picks everything between one and the last one picked, across days as well as within one. The line above the list then says how many are picked, with Clear. Dragging any picked task takes them all: the others leave their places the moment the drag starts, the copy under the pointer says "+N more", and they land together where it is dropped, in the order they had on the page. Dragging a task that is **not** picked moves that one alone and drops the picking, so what is about to move is never in doubt; a task whose own save is still running stays behind rather than travelling with a stale order. The picking is cleared once they have landed, and a picked task that is deleted or leaves the page simply stops counting (`selectedIds` is worked out as the list renders, never in an effect).
  - The keyboard moves a group the same way, because the group is worked out on the drag, not by the sensor: pick the tasks, focus a picked task's handle, Space, arrows, Space. Announcements say "3 picked tasks" instead of naming one.
  - **The list never rearranges itself under the pointer while a task crosses days, and this is not cosmetic.** It used to move the task into the day being crossed on every `onDragOver`; that reflow moved what the pointer was over, which reflowed the list again, until React gave up with error #185 ("maximum update depth exceeded") on the live site. The days are now taken once, at the start of the drag (only the tasks travelling with a group leave their places), and nothing but the **lit-up day under the pointer** changes while it runs. Within one day dnd-kit's own sortable strategy still slides the rows apart, which costs no state at all. Never reorder days from `onDragOver` again.
  - The whole move is worked out **on the drop**, from the days as they stood when it began: the day dropped into, and the index of the task dropped on (plus one when the pointer is past its middle, for another day; within a day the index is used as `arrayMove` would, so where it lands is where the list showed it). While dragging, the task follows the pointer as a lifted copy (`DragOverlay`). Today is always shown as a place to drop on, even with no tasks, on the page that shows it.
  - **The page is told once, on the drop.** It shows the new order at once and saves it through `PUT /api/daily-tasks/[id]/move` with `{ today, taskDate, orderedIds }`, the destination day's whole new order, `[id]` being the task that was dragged. **One task and a whole group are the same request**, because the order says for itself what moved: every id in it that is on another day now is a task arriving on this one. Moves are sent one after another (a promise queue), so a second quick drag is checked against the first one's result. A failed move puts the list back and reads it again from the server.
  - `moveTask` checks the order against the database first (every id must be a task the viewer may see, and none of the destination day's tasks may be missing from it), then sets the day on everything arriving and writes the day's positions in one ordered `bulkWrite`. A stale order answers 409, a task that is gone or belongs to another account 404, a day after today 400 (`MoveTaskSchema`, `lib/validation/dailyTasks.ts`, which also holds the shared date schemas).
  - Measured on a production build: a long drag across days runs with no long tasks and every frame within 17ms. `next dev` shows brief pauses from React's development mode, not from the feature, so judge smoothness on a build. `DayGroup` and `SortableTaskRow` are memoised so the days a drag does not pass through stay still.
- **States:** ticked is green (`success*` tokens), a day that has passed with the task still open is red with a cross (`error*`), everything else is plain. `PUT /api/daily-tasks/[id]` writes only `isCompleted` and `completedAt`; the page updates the checkbox at once and puts it back if the write fails.
- **`DELETE /api/daily-tasks?today=`** deletes every task older than the seven-day window in one bulk delete, behind `CleanupOldTasksDialog` (the shared `Modal`). Nothing is ever deleted automatically because a task got old.

### Temporary Quick Notes (`/quick-notes`, not a LinkedIn tool)
- A place to keep text worth reusing. **No AI, no prompts, no research:** the module only stores, lists, edits, copies and deletes, so it has no prompt record and never calls a provider.
- Two panels: saved notes on the left (newest first), and the save box on the right: an optional **Title** above the shared visual editor (`RichTextEditor` with `visual`, `fill` and `images`; Ctrl/⌘+Enter saves from inside it, the box clears on success and the list reloads from the newest note). The draft (title and content) is the `quick-notes:draft` store, version 2.
- **A note is formatted text** (the Markdown subset of `lib/richText.ts`), so every note saved as plain text before reads exactly as it did. The card shows it through `RichTextView` with `showImages`, its title above it when it has one; a note longer than `NOTE_PREVIEW_MAX_LENGTH` or holding a picture is shown to a set height with **Open it**.
- **Editing (`components/quick-notes/NoteEditorDialog`)**: the pencil on a card opens the note in the same editor with its title, and **it saves itself** `NOTE_AUTOSAVE_DELAY_MS` (1.5s, Important Content's pause) after the last change through `PUT /api/quick-notes/[id] { title, content }`, saying "Auto-saved at …". Saves never overlap, Close saves anything still waiting (and stays open if that fails), and leaving the page sends it with `keepalive`. A note emptied in the editor waits rather than failing, since content is required. The list takes each confirmed save in place and keeps its order (by when it was saved).
- **Images** (pasted, dropped or picked in the editor, PNG/JPEG/WEBP up to `NOTE_IMAGE_MAX_BYTES`, 4 MB) go through the app, `POST /api/quick-notes/images` with the bytes as the body, and are written into the note as `![](/api/quick-notes/images/<owner>/<file>)`. `GET` on that path redirects to a freshly signed link for the uploader or anyone who may see a note naming it (404 otherwise). They are stored under `LinkPilot/quick-notes/<owner>/`. **The naming, storing, showing and cleanup are shared with Important Content**: `lib/storedImages.ts` (`defineStoredImages`, with `lib/noteImages.ts` and `lib/contentImages.ts` as the two instances) and `services/storage/storedImages.ts`, with `services/quickNotes/images.ts` holding the note-specific part. An image is an attachment: taking it out of a note keeps it (Undo can bring it back), and it goes when the last note naming it is deleted (one, picked, Clear All or the account), after the note, with a storage failure only logged.
- **The list scrolls rather than paging.** `NOTES_BATCH_SIZE` (40) notes load at once and the next batch loads when an `IntersectionObserver` sentinel at the end of the list comes into view (with a "Load more notes" button as the keyboard and no-observer path). There are no Previous/Next controls.
- Paging is by **cursor, not offset**: `GET /api/quick-notes?cursor=<createdAt>|<id>` returns `{ notes, nextCursor, total }`, and `listNotes` asks for one row more than the batch to know whether `nextCursor` is needed. A cursor points at a note, so deleting notes never makes the next batch skip or repeat one; an unreadable cursor simply starts again from the newest note.
- The routes: `GET` a batch, `POST { content, title? }` to save, `DELETE` to clear everything, `PUT /api/quick-notes/[id]` to edit and `DELETE /api/quick-notes/[id]` for one note (both 404 when it is gone or another account's). POST and PUT validate with the one `QuickNoteSchema` (`lib/validation/quickNotes.ts`).
- A note is at most `NOTE_MAX_LENGTH` (20,000 characters, the same ceiling `constants/prompts.ts` uses) and its title at most `NOTE_TITLE_MAX_LENGTH` (120); empty or blank content is refused, and a note with no title works exactly like one with. The same text saved twice is two notes, on purpose.
- Each note shows the time it was saved (no id, no character count); **its copy button always copies the whole note** (`CopyButton` with the note's full `content`, exactly as saved).
- **One note deletes on a single click, with no confirmation** (they are small and easy to save again): the card leaves the list at once, the total follows, and a failed delete shows the error and leaves the note in place. Only **Clear All** confirms, through `ClearNotesDialog` (the shared `Modal`, so Escape and the backdrop cancel), and it touches only the `quick_notes` collection.
- Retries follow `lib/apiClient.ts`: the list (GET), the edit (PUT, which lands on the same text however often it is sent) and the deletes are retried on their own; Save (POST) is wrapped in `withIdempotency` and sent with `{ idempotent: true }`, so a retry can't save the note twice, and it also offers a Try again action. An image upload retries (a repeat only stores a copy nothing names).
- `tests/quickNotes.test.mjs` covers the title rules, the content rules, image paths and the shared image naming.
- Notes belong to the account that saved them (see Accounts and roles): Clear All deletes only that account's notes.

### Reference Content (`/reference-content`, not a LinkedIn tool)
- A library of **named** reusable text: how to create an API key, a client setup procedure, a troubleshooting note, a stock explanation. **No AI, no prompts, no research**; it only stores, searches, copies and edits.
- It sits under "Client Work", because it is the text sent to clients again and again, while Quick Notes stays under "Workspace". They stay separate on purpose: Quick Notes is untitled scraps you paste and drop (one-click delete, no search), this is curated material you keep, name, search and edit.
- Cards in a responsive grid (1 / 2 / 3 columns), newest first, each with **Copy** (always the whole text, however much the card shows), **Edit** and **Delete**. Text over `REFERENCE_PREVIEW_MAX_LENGTH` (320) is cut with a "Show all" toggle that opens it inside the card.
- **Add and Edit share one dialog** (`ReferenceItemDialog`, on the shared `Modal`), so editing starts from what was saved; an edited card updates in place instead of reordering the list. **Delete always confirms** (`DeleteReferenceDialog`, naming the item); Escape, the backdrop and Cancel all leave it alone.
- **Search** runs over the name *and* the text, case-insensitively, after `SEARCH_DEBOUNCE_MS` (300ms) of typing, and the search term is escaped so it stays plain text rather than a pattern. A search resets the list to its first batch, and the count in the header follows the search.
- **50 per request, enforced in `listItems`** (`Math.min(limit, REFERENCE_PAGE_SIZE)`), not just in the page: asking for more still returns 50. Paging is by cursor (`?cursor=<createdAt>|<id>`, the same shape Quick Notes uses) and the cursor and the search run in the same query, so paging inside a search never skips or repeats.
- Routes: `GET /api/reference-content?search=&cursor=` for a batch, `POST` to add, `PUT /api/reference-content/[id]` to edit, `DELETE /api/reference-content/[id]` to remove one.
- Limits: `REFERENCE_TITLE_MAX_LENGTH` (120) and `REFERENCE_CONTENT_MAX_LENGTH` (20,000, the app's usual ceiling); both fields are required, checked in the dialog and again by `ReferenceItemSchema` on the server.

### Meeting Notes to Tasks (`/meetings`, not a LinkedIn tool)
Reads a meeting of any length. A 5 hour transcript (1.5M characters, 131 parts) is a tested case, not a hope.

- **The transcript is saved before anything is analyzed** (`POST /api/meetings` answers in under a second) and is never touched by a run, so a failed or repeated analysis can never cost the source. It is also never sent to the history list, which reads a projection of summary fields only.
- **Map, then reduce.** `lib/transcriptChunks.ts` splits the transcript at speaker turns and paragraph ends into `CHUNK_MAX_CHARS` (12,000) parts, each carrying the tail of the part before it as context; every character lands in exactly one part, so nothing is silently dropped. `analyzeChunk` reads one part (the map), and `synthesizeMeeting` turns the parts into the meeting (the reduce).
- **The lists are merged in code, not by a model** (`services/meetings/aggregate.ts`). A model asked to merge 131 sets of notes summarises them, and a decision from the middle of the meeting disappears; instead every participant, decision, task and request from every part is carried across and de-duplicated here (near-duplicates fold by containment, and an owner or deadline any part stated is kept). The model is left with what needs judgement: the title, the purpose, the topics, the minutes. Only if the merged notes are too big to read at once are the parts folded hierarchically first, and only for what the model sees.
- **The run is resumable and bounded, with no queue.** `POST /api/meetings/[id]/process` reads at most `CHUNKS_PER_REQUEST` (6) parts, `CHUNK_CONCURRENCY` (3) at a time, writes each result as it lands and answers with `{ status, progress, hasMore }`. The page (`hooks/useMeetingRun.ts`) keeps calling while `hasMore`. So no request runs long enough to be cut off on a serverless host, closing the browser loses nothing, and a retry re-reads only the parts that are missing. Statuses: `saved` → `analyzing` → `summarizing` → `completed`, plus `failed` (the reason is stored on the meeting) and `stale`.
- **Editing the transcript invalidates the analysis**: the chunk results are deleted, the status becomes `stale`, and the page says the analysis came from the earlier transcript until Re-analyse (`{ restart: true }`) rebuilds it. Editing only the name leaves the analysis alone.
- A meeting saved without a name gets its title from the analysis (`isTitleGenerated`); a name typed by the user is always kept.
- **Nothing is invented.** Every participant, decision and task carries `evidence` ("stated" or "inferred", shown in the UI), the participant count follows the people actually listed, and what the meeting left open goes under `unknowns` instead of being filled in.
- Prompts: `meeting-chunk` and `meeting-synthesis` are editable through the usual Update Prompt editor; `meeting-system` holds the fixed rules and is not editable.
- The history is searched by name in the database with a status filter and cursor paging (`MEETINGS_PAGE_SIZE` 20), and refreshes itself every few seconds while any meeting is being analyzed.
- **The list is a table from `xl` and cards below it** (`components/meetings/MeetingsTable`, min-w-[880px], the breakpoint its width asks for; see Responsive layout): what the meeting was about, where its analysis has got to, how long the transcript is with how many people were in it, when it was saved, and **Open and Delete on every row**. The title is the link in both layouts, so a meeting opens in one click wherever it is read. Deleting from the list always confirms first (`DeleteMeetingDialog`, naming the meeting), because a meeting takes its transcript, its analysis, its chunks, its vectors and its chat with it; the row leaves once the server confirms and the count follows, and a delete that fails leaves the meeting where it was and says why. Paging stays as it was: the next batch loads as the end of the list comes into view, with a Load more button behind it.

### Recording a meeting (`/meetings/record`, part of Meeting Notes to Tasks)
- **Record a meeting** on the meetings list opens `app/meetings/record`: an optional name, "My microphone" and "My camera", then Start, which asks the browser for a screen or tab to share (tick its audio, or the others aren't heard). While it records the page shows the clock, Pause/Resume, Stop, a small preview, and the upload in MB and percent with the chunks sent and on their way. Stop waits for the last chunk, then opens the meeting.
- **What it listens to** (`RECORDING_SOUND_MODES`): **My voice and the laptop's sound** (the default: a meeting, a WhatsApp call, a video) or **Only my voice** (the microphone is the whole recording, so it can't be switched off, and no sound is asked of the share). Other people's voices come out of the speakers and reach the recording only as the share's own sound, so in the first mode a share **without sound is refused before anything is saved**, with what to fix for what was shared (a window never carries sound; a tab needs "Also share tab audio"; Entire screen needs "Also share system audio"). The share asks for system audio and takes the laptop's sound raw (no echo cancelling, noise suppression or gain control, which thin out other voices). While it records, a meter for each side (`SoundMeter`, in words as well as colour) shows it is coming through, each judged at its own level (`LAPTOP_HEARD_LEVEL`, `VOICE_HEARD_LEVEL`: digital sound has no hiss, a microphone always hears the room), and a warning shows when the laptop's side has been silent for `MEETING_SILENCE_WARN_MS` while you are heard.
- **The recorder lives outside React** (`lib/meetingRecorder.ts`, read through `hooks/useMeetingRecorder`), so moving to another page of the app keeps recording; leaving the site asks first. Three `MediaRecorder`s run side by side: **screen** (the shared video plus one audio track that mixes the meeting's sound and the microphone through an `AudioContext`), **camera** (its own file: a recorder takes one video track, and drawing two into one canvas freezes while its tab is in the background), and **audio** (the same mixed sound, restarted every `AUDIO_SEGMENT_MS`, 5 minutes, or at `AUDIO_SEGMENT_MAX_BYTES`, so each piece is a whole small file that can be written out on its own; a chunk of the video stream can't be decoded by itself).
- **Chunks of at most 4 MB (`RECORDING_CHUNK_MAX_BYTES`) go up while it records**, one `PUT /api/meetings/[id]/recording/chunks?track=&index=` each, the body being the bytes. The stream is cut at exactly 4 MB (`cutChunks` in `lib/recordingParts.ts`) and whatever has gathered is sent at least every `RECORDING_FLUSH_MS` (10 s), so a closed tab loses seconds. **They go through the app's route, not straight to S3, on purpose**: 4 MB fits Vercel's 4.5 MB request body limit, and the bucket's CORS rule refuses browser uploads from the live site (see Important Files), so this is what works the same locally, on any port, and on Vercel. The route writes the chunk with `putObject` under a key it builds from the meeting's own id and records its size in one request (`storeChunk`); the same chunk twice lands on the same key. Two uploads run at once; a failed one waits `UPLOAD_RETRY_MS` and goes again, never dropped, and the page says the connection dropped. **Pause** pauses the recorders and the uploads together; the clock leaves paused time out.
- **Stop** stops the recorders, sends what is left and calls `POST …/recording/finish` with how many chunks each track made: all of them must already be stored (409 otherwise, and the page waits and asks again). A recording whose tab closed shows on its meeting page with **Finish with what was uploaded** (`{ partial: true }`: each video up to its first missing chunk, every audio piece that landed).
- **Joining and writing out are short resumable steps** (`POST …/recording/process`, `runRecordingStep` in `services/meetings/recording.ts`, `maxDuration` 60, each step stops starting work after `RECORDING_STEP_BUDGET_MS`), driven from the meeting page by `hooks/useRecordingRun` while `hasMore`, like the analysis. **Joining**: S3 refuses multipart parts under 5 MiB, so the server reads the chunks and sends runs of them as parts (`groupIntoParts`: two 4 MB chunks make one part; one short recording is a single `putObject`), recording each part sent so a cut-off step resends at most one, then completes the upload and deletes the chunks. The recording's length is written into the WebM header first (`setWebmDuration`, `lib/webmDuration.ts`: a MediaRecorder can't know it, so without this the video shows no length and can't be seeked). **Writing out**: `SEGMENTS_PER_STEP` audio pieces a step, each read from S3 and sent to **Whisper on Groq only** (`transcribeRecording` with `providers: ["groq"]`); silence is an empty piece, not a failure. The transcript is the pieces in order, each marked with where it starts (`[5:00] …`), and it goes on the meeting with status `saved`, so **the ordinary analysis takes over** and writes the notes and, with no name given, the title.
- **No OpenAI anywhere in a recorded meeting.** The process route runs with `runAiRequest(…, { without: ["openai"] })`, and the analysis route leaves OpenAI out too for a meeting with a `recording`. When Groq's daily tokens are used up (all keys share one quota), the analysis stops with that reason and **Analyse again** carries on later; it does not fall back to OpenAI.
- **Where it is** (`recording.stage`): `recording`, `consolidating`, `transcribing`, `done`, or `failed`, which the next step resumes from where it stopped. The meeting's own status adds `recording` and `transcribing` before the usual ones. The meeting page shows the progress of both steps, then the video (a signed link, `GET …/recording`, `no-store`) with the camera in a corner kept in step with it, and a download link.
- **Notes** (every meeting, not only recorded ones): when an analysis completes, `buildMeetingNotes` (`lib/meetingNotes.ts`) lays it out as editable rich text (summary, purpose, who was there, topics, decisions, my tasks, action items, what the client asked for, what is still open; empty sections left out) into `notes`. The meeting page shows them with **Edit** (`RichTextEditor`) and saves through `PUT /api/meetings/[id]/notes`. Once edited, `notesEditedAt` is set and a new analysis leaves them alone; saving them empty lets the next analysis write them again. The name stays editable with the meeting's Edit, as before.
- **A meeting deleted while its recording is still arriving or being joined leaves nothing behind**: a chunk that lands after the delete is removed at once (`storeChunk` checks the write matched), and a joining step that finds the meeting gone deletes the file it just finished or aborts the upload it opened, then stops.
- **Storage**: everything under `LinkPilot/meeting-recordings/<meeting id>/` (`recordingKeys`): `screen.webm`, `camera.webm` and `audio/<n>.webm` once joined (chunks only until then). Deleting a meeting, several meetings, or an account removes them (`removeRecordingFiles`, keys built from what the meeting recorded, never by listing the bucket); a recording is an attachment, so the meeting goes first and a storage failure is only logged.
- `tests/meetingRecording.test.mjs` covers the header rewrite, the cutting and the part grouping (every chunk in exactly one part, each part but the last at least 5 MiB), the keys and the notes layout.

### Deleting several records at once (every module that lists records)
- **One pattern, one look:** `components/ui/BulkDelete.tsx` (`BulkDeleteBar`, `ConfirmBulkDelete`) and `hooks/useRowSelection.ts` are what every list uses, so ticking rows and deleting them read the same everywhere. A tick box sits on each row (Shift picks a run), the bar above the list offers **Delete N picked**, and where a module can delete by filter it also offers **Delete all N matching**. Every one of them confirms first, in a dialog naming the exact count, and says what else goes with each record. Nothing deletes without that confirmation.
- **The filters decide what goes.** Each service builds the records to delete from the same filter its list builds (`matchingFilter` in `services/savedOutputs.ts` and in `services/importantContent/entries.ts`, the same `narrowing` in meetings and employees), so a bulk delete can never reach a record the page would not have shown. **The two forms are scoped differently, on purpose:** ticked rows use `visibleTo(viewer)`, so an admin may delete a row they can see, exactly as the single-row delete always has; a whole filter uses `ownedBy(viewer)`, like Clear All and the Daily Tasks cleanup, so "delete all matching" can never reach another account's records, not even an admin's (it takes their own and the records saved before accounts existed). A user only ever deletes their own either way, and an id belonging to another account matches nothing. Checked against the database for each module, including the admin case.
- **What each module deletes, and what goes with it:**
  - The ten "view all" pages: `DELETE /api/saved-outputs/[tool]` (ids or `all`, with the list's filters).
  - Important Content: `DELETE /api/important-content` (ids or `all`, with the search and type).
  - Reference Content: `DELETE /api/reference-content` (ids or `all`, with the search).
  - Meetings: `DELETE /api/meetings` (ids or `all`, with the search and status); each meeting takes its chunks, its vectors and its chat.
  - Employees: `DELETE /api/employees` (ids or `all`, with the search and status); each employee takes their daily plans.
  - Daily Tasks: `DELETE /api/daily-tasks` with `{ ids }` deletes the picked tasks; with no body it is still the week-old cleanup.
  - Quick Notes: `DELETE /api/quick-notes` with `{ ids }` deletes the picked notes; with no body it is still Clear All.
  - Existing Topics: `DELETE /api/trending-topics/history` (`{ topics: [{ searchId, title }] }` or `all`, with the list's filters). A topic lives inside its search, so each search is rewritten once (`$filter` on `result.topics`, then `topicCount` from what is left) and **the search itself is never deleted**, even when its last topic goes, exactly as deleting one topic has always behaved.
  - Important Files: `DELETE /api/important-files` (ids or `all`, with the search and type). **The object goes before its record**, one file at a time, so a storage failure leaves the file listed rather than losing track of it; the answer carries `failed` and the page says how many could not be removed.
  - The Post Image gallery: `DELETE /api/post-images` (ids or `all`, with the gallery's filters), the same way: the picture goes from storage before its record, and an image that cannot be removed stays listed.
  - Deleting an employee (one or several) also clears the images their plan tasks carried (`planTaskImagesOf` + `deleteTaskImages`, records first and objects after, owned by the task-attachments work).
- **Two rules for deleting something that also lives in storage, and which one applies is a decision, not an accident:**
  - **The object is the record** (Important Files, the Post Image gallery): the object goes **before** its record, one at a time, so a storage failure leaves the record and nothing is ever lost track of. The file stays listed, counts in `failed`, and the page says so ("3 files deleted. 1 could not be removed from storage and is still listed"), which gives the user something to act on.
  - **The object is an attachment** (a task's image): the record goes **first** and the object after, and a storage failure is logged and swallowed, because the delete the user asked for must still succeed. The worst case is an invisible orphan rather than a task that will not go away.
- **Deliberately left alone:** the admin **Audit log** (it is the security trail, and bulk deletion would defeat it) and **User Management** (an account already has its own delete behind a typed email, and it removes everything that account ever made).
- `BulkDeleteSchema` (`lib/validation/listFilters.ts`) is the shared body: `{ ids }` or `{ all: true }`, never neither.
